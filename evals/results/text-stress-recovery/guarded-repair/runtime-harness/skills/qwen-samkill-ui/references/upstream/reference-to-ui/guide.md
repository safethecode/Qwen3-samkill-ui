# 레퍼런스 기반 UI 구현

목표는 AI의 관성적인 디자인에서 벗어나 레퍼런스와 제품에 필요한 아이디어를 결합해 좋은 제품을 구현하는 것이다. 레퍼런스의 구조·시각 문법을 분석하고 새로운 선택의 목적을 설명한다. 색상 복제나 금지 목록 통과만으로 완료하지 않는다.

## 필요한 입력

사용자 과제, 대상 화면, 브랜드/기존 디자인 시스템, 실제 확인한 레퍼런스 또는 출처가 표시된 사용자 관찰 기록. 기존 프로젝트에서는 관련 화면과 토큰을 확인한다. 새 프레임워크나 컴포넌트 라이브러리를 강제하지 않는다. 명세만 요청하면 계약과 검증 계획을 전달하고 종료한다. 코드·실제 렌더 실행을 요구하지 않으며 상태는 `spec-only`다.

레퍼런스가 필요하면 설치된 `uibowl-research`를 사용한다. 복합 제품은 핵심/보조 과제별 B-ID로 조사하고 모든 주요 영역에 실제 레퍼런스 근거를 연결한다. 채팅 요청 때문에 Todo 목록 등 원래 제품을 조사에서 빠뜨리지 않는다. 이미 충분한 brief가 있으면 재검색하지 않는다. 해당 스킬이 없으면 현재 사용 가능한 도구로 같은 근거를 확보한다. 이미지에 접근하지 못하면 기존 시스템과 요구에 따른 임시 설계는 진행하되 `reference-unverified`로 표시한다. 이 상태는 직접 이미지 미확인이라는 뜻이며 출처를 밝힌 사용자 관찰 기록을 무효로 만들지 않는다. 직접 본 화면과 전달받은 관찰은 구분한다.

## 레퍼런스를 받은 직후

[reference-decompose](../reference-decompose/guide.md)로 원본을 요소·관계·조립 계약으로 먼저 번역한다. 이미 있는 상세 분석은 재사용한다. 제품 적용 결정을 원본 관찰에 덮어쓰지 않고, 사용자 요청이 프롬프트 검증 실험이면 요소별 표본과 조립 화면을 함께 비교한다.

## 산출물과 첫 화면의 작업 순서

형식을 지정하지 않은 UI 디자인 요청은 기존 기술과 도구에 맞는 **수정·렌더 가능한 화면**을 기본 산출물로 삼는다. HTML/CSS 프로토타입, 기존 앱 화면, 편집 가능한 디자인 파일 등이 해당한다. 전체 UI를 이미지 생성 결과로 대신하지 않고, 이미지 생성은 필요한 사진·삽화 등 에셋에 활용한다. 사용자가 이미지 시안만 명시하면 그 형식을 따르며, 명세만 요청하거나 읽기 전용인 작업에는 구현을 추가하지 않는다. ‘디자인’이라는 표현만으로 임의로 `spec-only`로 축소하거나 실제 서비스·배포까지 확장하지 않는다.

구현은 [핵심 화면의 첫 비교](references/reference-synthesis.md#핵심-화면의-첫-비교)를 거친 뒤 의존하는 다른 화면으로 확장한다. 핵심 화면 하나에 실제 길이의 내용을 넣어 렌더하고, 주 레퍼런스와 같은 표시 폭에서 구조·위계·밀도를 직접 비교한다. 문서 작성이나 생성 프롬프트를 이 비교 대신 사용하지 않는다. 이 단계는 내부 검수이며 매번 사용자 승인을 다시 받으라는 뜻이 아니다.

## 레포 디자인 맥락

대상 레포 루트의 `DESIGN.md`를 먼저 읽고 현재 제품 기준을 적용한다. 없으면 구현 전 `design-md`로 기존 UI·토큰·레퍼런스를 분석해 작성한다. 기존 문서 갱신도 해당 스킬을 사용하며 사용할 수 없으면 같은 분석과 보존 원칙으로 직접 작성한다. 디자인 기준이 바뀌면 루트 문서와 실제 토큰/구현을 함께 갱신한다. 상세 계약은 기존 경로에 유지하고 루트 문서에서 연결한다.

## 구현 전 계약

글자·폰트·줄바꿈을 다룰 때는 [실제 내용의 타이포그래피](references/typography.md)를 읽는다. 인터랙티브 컴포넌트·폼·비동기 행동은 [내용 경계와 연속 상태 검증](../reference-review/references/state-stress.md)으로 도달 가능한 입력·전이와 검증 조건을 계약한다. 이미 있는 계약에 연결하고 작은 수정에 불필요한 표본 앱을 만들지 않는다.

[UI 구성과 실제 실패 방지](references/ui-composition.md)를 반드시 읽는다. 임의 로고 금지, 읽는 글자 기본14 CSS px 및 해당 문서의 제한적12px 예외, CTA/필터 구분, 보조 문구 삭제·배치, 의미 있는 아이콘, 불필요한 구분선·스크롤 제거를 적용한다. 목록과 대화처럼 다른 과제가 공간을 경쟁하면 탭/별도 뷰를 검토한다. 생성/수정 표면의 주 제목, 날짜·시간 입력의 제품 스타일, 부모/자식·상태별 여백, 모든 화면의 톤 일관성도 검증한다. 서로 다른 섹션은 과제에 맞는 간격·제목·표면 단계로 구별한다.

[제품의 본질에서 배치하기](references/product-reasoning.md)를 먼저 읽는다. 사용자·문제·핵심 행동·필요한 정보를 정의하고, 중요한 요소마다 배치/강조 이유를 연결한다. 레퍼런스에서 유지할 원리와 새 아이디어의 역할·검증 방법을 기록한다. 기존 요구로 알 수 있는 내용을 되묻지 않는다.

[레퍼런스 장점의 결합과 품질 검증](references/reference-synthesis.md)을 반드시 읽고 Q-ID별 채택 특징·구현 요소·비교 근거를 정한다. 기능이나 색 일부만 가져온 것을 레퍼런스 반영 완료로 보지 않는다.

[적용 형식](references/application-format.md)과 [근거 없는 디자인 방지 규칙](references/design-guardrails.md)을 읽고 프로젝트 문서 위치 또는 `design/design-contract.md`에 작성한다. 작은 수정은 채팅의 짧은 계약으로 충분하다.

1. 화면별 주 레퍼런스와 핵심 과제를 연결한다. 누적한 여러 출처의 좋은 부분을 역할별 보조 패턴으로 결합하고, B-ID마다 R-ID→D/Q-ID→구현 대상을 남긴다. 마지막 검색 결과만 적용하지 않는다.
2. 구조·읽기 순서·밀도·타이포그래피·색상 역할·표면·행동을 결정한다. 각 D-ID에 출처 O-ID 또는 요구사항, 구현 대상, 검증 기준을 붙인다.
3. 이번 화면의 **Do / Avoid / Intentional differences / Unknown**을 기록한다. Avoid에는 배제할 구체 요소, 근거, 대안을 쓴다. 해당하지 않는 항목을 개수 맞추기로 만들지 않는다.
4. 값은 `measured / estimated / chosen / existing-token`으로 구분한다. 시각 추정한 반경을 제품 공식 토큰으로 부르지 않는다.

패딩·버튼 글자색·아이콘까지 포함한 E-ID 상세 기록이 있으면 인계받는다. 없으면 대상 화면의 서로 다른 요소/변형별로 크기·사방 여백·글자·배경/글자/아이콘/테두리 조합·아이콘 선/채움·상태를 보완한다. 이미지 px와 CSS px를 분리하고 모르는 속성은 unknown으로 남긴다.

사용자 지정 브랜드와 과제 요구가 레퍼런스와 다르면 이를 의도적 차이로 남긴다. 디자인 시스템의 알려진 사용성 결함은 근거와 함께 수정한다. 색상·반경·그라디언트의 일괄 금지로 사용자 선택을 덮어쓰지 않는다.

## 구현

사용자 교정이 있는 작업은 [재발 점검](../reference-review/references/feedback-regression.md)에서 현재 과제에 해당하는 실패를 먼저 확인한다. 목록·저장·내역·빈 상태에 동일 컴포넌트를 확장할 때도 목적·정보·행동·기간/수량·복구를 각 뷰에 맞게 정하고, 이전 화면의 구조를 그대로 복제하지 않는다.

[디자인 토큰 계약](references/design-tokens.md)을 반드시 읽고 스타일 구현 전에 적용한다. 기존 토큰을 확인해 재사용하고, 채택한 시각값을 기본값 → 의미/역할 → 필요한 컴포넌트 변형으로 연결한다. 디자인만 요청해도 토큰 명세를 전달한다. 실제 코드 요청은 토큰 파일뿐 아니라 컴포넌트의 사용까지 확인한다.

호버·선택 등 상태 변화에는 토큰 계약의 모션 기준을 적용한다. 짧은 전환을 일관되게 사용하되 기능 반응을 늦추지 않고 동작 줄이기 설정을 지원한다.

기능 아이콘은 React에서 `lucide-react`, 비 React에서 공식 Lucide SVG/해당 환경 패키지를 기본으로 사용한다. 임의 SVG 경로를 제작하지 않는다.

코드를 작성할 때 [anti-slop 코드 기준](references/anti-slop-code.md)을 적용한다. TS/JS에서는 일반 규칙과 실제 lint/typecheck 결과를 확인하며 타입 단언이나 검사 완화로 통과시키지 않는다. 다른 언어에는 해당 검사를 실행했다고 주장하지 않는다.

레이아웃과 실제 내용 → 타이포그래피/간격 → 표면 → 동작 순서로 작업한다. 제품과 무관한 KPI, 홍보 히어로, 장식 카드를 추가하지 않는다. 가능한 기존 토큰을 재사용하고 필요한 변형만 만든다. 실제 길이의 한국어·가격·날짜·항목 수를 사용한다. 생성한 데모 데이터는 데모임을 명확히 한다.

모바일이면 [mobile.md](references/mobile.md), 데이터 작업 화면이면 [dashboard.md](references/dashboard.md)를 필요한 것만 읽는다. 로딩·빈 결과·오류·긴 내용·포커스·비활성 등 관련 상태를 구현한다. 스크린샷의 외형으로 API 동작을 추정하지 않는다.

한국어 UI 문구를 새로 쓰거나 바꾸면 설치된 `ux-copy`의 한국어 기준을 적용한다. 없으면 쉬운 말, 즉시 행동 예측, 중복 제거, 비용·조건 보존, 선택 존중을 기준으로 검토한다. API나 프레임워크 용어를 사용자 화면에 그대로 노출하지 않는다.

## 검증과 종료

실제 렌더를 목표 뷰포트에서 확인하고 D-ID별 시각/행동 기준을 검증한다. 설치된 `reference-review`가 있으면 그 기준을 사용한다. 없으면 계약과 구현 스크린샷을 직접 비교한다. 수정 권한 내에서 중요한 차이를 고친 뒤 해당 항목을 재검증한다.

reference-review의 공통 실패 목록과 이번 제외 목록으로 디자인 게이트를 실행한다. 기존 실패·예외 기록도 읽고 재발을 확인한다. 제품 핵심 과제 완료와 디자인 품질을 별도로 검사하며 FAIL/UNVERIFIED를 완료로 처리하지 않는다. 해당 스킬/판독 도구가 없으면 같은 기준으로 검토하되 자동 게이트 미실행을 남긴다.

완료 보고: 채택한 구조, 이유 있는 배제, 의도적 차이, 토큰 정의/사용 위치와 직접값 예외, 확인한 뷰포트/상태, 남은 미검증. 빌드 성공이나 머릿속 렌더링을 시각 검증으로 대체하지 않는다. 도구가 없으면 구현을 전달하고 시각 검증 미완료를 명시한다. 별도 배포·외부 전송 권한을 이 스킬에서 만들지 않는다.
