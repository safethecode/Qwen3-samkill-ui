# 리뷰 기준과 예시

## 비교 항목

| 순서 | 확인할 것 | 실패 신호 |
|---|---|---|
| 구조/과제 | 핵심 데이터·행동, 탐색·비교·선택 | 주문 표가 대형 카드로 대체되어 비교 작업을 방해 |
| 위계/밀도 | 읽기 순서, 첫 화면 정보량, 필요한 여백 | 필요 없는 hero/KPI가 실제 작업을 아래로 밀어냄 |
| 글자/내용 | 긴 한국어, 가격·날짜·단위, 줄바꿈, 대비 | 말줄임으로 식별 불가, 과제와 무관한 데모 통계 |
| 색/표면 | 브랜드·색상 역할, 반경, 선, 그림자 | 이유 없는 무지개 배지, 카드 안 카드, 장식 glow |
| 행동/상태 | 키보드·터치, 선택/오류/로딩/빈 결과, 복구 | hover-only 행동, 화면 캡처로 API 성공 추정 |
| 반응형/일관성 | 목표 폭/높이, 다른 화면의 공통 토큰, 스크롤 | 레퍼런스에 없는 모바일 동작을 검증된 것으로 주장 |

## 요소와 토큰 대조

- 읽는 UI 텍스트는 [굵기 하한](../../reference-to-ui/references/ui-composition.md#글자-굵기-하한)에 따라 computed font-weight가 최소 medium(500)인지 확인한다. 본문·보조문구·입력값·placeholder·버튼·탭·배지·오류·비활성 상태의 500 미만은 실패다. 토큰 이름만 medium이고 실제 값이 400인 경우도 포함한다. 제목·강조의 600/700을 500으로 낮추는 일괄 수정도 실패이며 아이콘·로고 이미지는 이 텍스트 규칙의 수정 대상이 아니다. 폰트 지원·대비·좁은 폭 줄바꿈은 별도로 검증한다.

아이콘/좁은 조작 모음은 [아이콘 영역 계약](../../reference-to-ui/references/icon-controls.md)을 적용한다. 실제 그림·슬롯·클릭 영역·focus의 차이와 확장된 영역의 이웃 충돌을 기록한다. 경계와 확장 영역을 눌렀을 때도 의도한 한 행동만 실행되는지 확인하며 선언된 크기나 접근성 이름만으로 조작성을 통과시키지 않는다.

- E-ID별 위/오른쪽/아래/왼쪽 시각 거리, 외부 간격, 자식 gap, 폭/높이, 텍스트 정렬을 비교한다. 이미지 좌표와 CSS 단위·배율이 다르면 수치 동일 여부를 판정하지 않는다.
- 버튼은 배경뿐 아니라 글자색/크기/굵기/줄높이, 아이콘색, 테두리, 반경, 상태를 한 묶음으로 검사한다. 흰 글자가 검정으로 바뀐 경우 ‘버튼 색상 일치’로 닫지 않는다.
- 아이콘은 outline/filled, 선 굵기, 끝/모서리, 광학적 크기/박스, 글자와 gap/수직 정렬을 본다. 비슷하다는 이유로 아이콘 패밀리까지 동일하다고 하지 않는다.
- 토큰 정의·별칭·실제 사용을 확인한다. 미정의/순환 참조, 같은 역할의 중복 토큰, 컴포넌트 직접값 덮어쓰기, 배경만 바뀌는 불완전한 테마/상태 매핑을 점검한다. 토큰 원본·매핑된 유틸리티·구조상 필요한 값·설명된 예외는 하드코딩 결함과 구분한다.
- 발견한 차이는 D/E-ID 및 토큰 이름/사용 파일에 연결하고 영향에 따라 우선순위를 정한다. 1px 차이와 읽을 수 없는 글자를 같은 심각도로 취급하지 않는다.
- 토큰 코드 검사는 렌더 없이도 확인 가능한 범위가 있지만 실제 대비·패딩 인상·아이콘 정렬 검증은 렌더 근거가 필요하다. 두 결과를 분리한다.

효과가 없다는 관찰과 효과를 넣지 않겠다는 결정은 다르다. 원본 정지 이미지로 원본 애니메이션 부재를 판정하지 않는다. 실제 구현 렌더가 없으면 색·정렬의 확정 결함을 만들어내지 않는다.

한국어 문구를 검토할 때는 설치된 `ux-copy`의 한국어 기준을 함께 적용한다. 번역투, 같은 말의 반복, 버튼과 바로 다음 행동의 불일치, 숨겨진 비용·조건, 거절에 부담을 주는 표현을 확인한다. 실제 문자열을 전달받았다면 텍스트 자체는 검토할 수 있다. 문자열 문제 확인과 화면 배치·클릭 동작 확인은 별도로 기록한다.

## 가상 리뷰 예시

입력: R1 사용자 관찰은 주문 20행 테이블. D1 계약은 행 기반 비교. 개발자는 빌드 통과와 “KPI 4개, 주문 카드 6개”라는 구현 설명만 전달. 실제 구현 이미지 없음.

총괄: **not-verified**. 레퍼런스 적합성과 행동은 실제 화면으로 확인하지 않았다. 빌드 통과는 전달된 빌드 결과다.

| ID/기준 | 근거 | 차이/영향 | 우선순위·상태 | 다음 작업 | 재검증 |
|---|---|---|---|---|---|
| V1/D1 | 사용자 R1 관찰 + 구현 설명 | 행 비교 구조가 카드로 바뀌었을 가능성. 대량 주문 비교 저해 우려 | P1 suspected | 실제 렌더에서 구조를 확인. 사실이면 주문 목록을 정렬된 표로 수정 | 같은 뷰포트에서 열 비교·정보량·일괄 선택 수행 |
| V2/행동 요구 | 실행 근거 없음 | 선택·실패 복구 결과 미상 | priority-unassessed, not-verified | 관련 행동 실행 | 결과와 근거 경로 기록 |

스크린샷 부재 자체를 제품의 P0 버그로 부르지 않는다. 설명만으로 “배지가 6색이고 반경은 24px”처럼 입력에 없는 결함을 만들지 않는다.

## 수정 권한이 있는 경우

확인된 문제 중 사용자 영향이 큰 순서로 고친다. 정상 브랜드·공통 레이아웃까지 교체하지 않는다. 해당 D/V-ID를 유지하고 수정 파일, 재검증 뷰포트·상태·결과를 적는다. 구현 변경 뒤 이전 스크린샷을 최신 증거로 재사용하지 않는다. 전체 렌더가 어려우면 검증한 부분과 남은 부분을 나눈다.

수정 전후 리뷰 항목을 닫으려면 해당 문제의 실제 재검증 근거가 필요하다. 코드 변경이나 추론만으로 `fixed-and-verified`로 바꾸지 않는다.

## Todo 실사용 피드백에서 드러난 판독 누락

토큰화·기능 동작·겹침 해소만으로 화면 구성이 적합하다고 판단하지 않는다. [UI 구성 기준](../../reference-to-ui/references/ui-composition.md)에 따라 다음을 직접 확인한다.

- 요청/제공 자산 없이 만들어진 로고와 슬로건을 ‘제품 식별’로 합리화하지 않았는가.
- 읽는 글자의 computed size가 기본14 CSS px 이상인가. 보조정보12px 예외는 ui-composition의 적용 조건·선택자 범위·가독성/확대 증거를 확인한다. 선언 없는14px미만,12px미만,행동/입력/핵심 안내로의 확대는 실패다. 기본·좁은 폭·상태별로 확인하고 토큰 선언만으로 끝내지 않는다.
- 필터/탭/CTA의 역할이 기본 상태에서 구별되는가. ‘편집’이 비활성 필터와 같은 텍스트로 보이지 않는가.
- 힌트가 필요한 입력 곁에 있는가. 제거해도 잃는 정보가 없는 제목 옆 문구·중복 안내가 남지 않았는가.
- 기능 아이콘의 출처·의미와 사용 위치가 타당한가. 출처 없는 로고 예외로 정렬/색 검사를 우회하지 않았는가.
- hr 유무와 반복 횟수에 관계없이 영역 구분 바, 탭 하단 기준선, 선택 밑줄/이동 바가 남아 있는가. border/pseudo-element/shadow/gradient/SVG 등 구현 수단과 무관하게 최종 화면으로 판독한다. 버튼 테두리·키보드 포커스·실제 데이터 시각화까지 없애지는 않는다.
- 빈 상태·1개·소수 항목에서도 형제 영역 때문에 불필요한 스크롤이 생기는가. overflow 숨김으로 문제를 가리지 않았는가.
- 목록과 채팅이 서로 압축하지 않는가. 대화 전송/오류/복구/과거 메시지 읽기/전환 복귀가 자연스러운가.

각 판정에는 실제 selector/상태/뷰포트와 관찰을 연결한다. 전체 파일이나 스크린샷 해시만 반복하고 차이·위치가 없는 보고서는 판독 근거로 충분하지 않다. 새 사용자 교정은 과거 aligned 판정과 함께 보존하고 현재 기준으로 다시 판단한다.

## 생성 폼·부모 여백·화면 간 일관성

- RUI-20: 생성/수정의 목적 제목이 body 크기의 전역 h2로 내려가지 않았는지 실제 주 제목 역할과 라벨 대비를 확인한다. 의미 heading level과 시각 크기를 구별한다.
- RUI-21: 날짜/시간 표시·트리거·선택 상태·아이콘/포커스가 제품 입력 체계에 맞는지 검사한다. 브라우저 기본 표현이 노출됐는지, 실제 선택·취소·초기화와 저장값이 맞는지 실행한다.
- RUI-22: 부모 패딩, 첫/마지막 자식 margin, gap, 자식 내부 패딩을 분리해 computed 박스와 비교한다. 완료 상태 추가 margin으로 윗여백만 커지거나 형제 기준선이 바뀌는지 확인한다.
- RUI-23: 목록/완료/빈 대화/진행 대화/생성/수정을 동일 폭의 실제 화면 묶음으로 대조한다. 같은 역할의 제목·입력·버튼·표면·좌우 여백이 토큰과 실제 모습 양쪽에서 일치하는지 본다.

명세, HTML 태그, 토큰 이름만으로 통과하지 않는다. 사용자 캡처로 외형 문제를 기록할 수 있지만 실제 CSS 크기와 클릭/선택 동작은 코드·렌더·실행 근거를 구별한다.

RUI-25: 서로 다른 작업 영역의 시작/끝과 소속 관계가 실제 화면에서 구별되는지 확인한다. 섹션 내부와 사이의 간격, 제목, 표면 단계를 과제와 레퍼런스에 대조한다. 구분선을 없앤 뒤 경계도 사라졌거나 모든 영역을 같은 카드로 감쌌다면 다시 구성한다. 단일 과제 화면에는 불필요한 섹션을 강제하지 않는다.

입력창/버튼 정렬 추가: 빈·한 줄 입력의 내부 텍스트와 아이콘/실행 조작이 의도한 세로 중심에 놓이는지 확인한다. 부모 flex center만 검사하지 말고 자식 line-height/padding/높이와 실제 줄 상자를 대조한다. 여러 줄 textarea의 위쪽 읽기 시작점과 본문 왼쪽 정렬은 보존한다. 선택 기능 힌트 삭제 후 예약된 footer 높이까지 제거됐는지 검사한다. RUI-11/22와 ORC-F10/G18에 연결하며 한 상태만 transform으로 맞춘 결과는 재검토한다.

입력 포커스: 실제 초점은 input/textarea에 있고, 시각적 표시는 필드 경계를 소유한 컨테이너의 inset box-shadow에 있는지 검사한다. 내부 입력 자체의 inset shadow, border 변경만으로 만든 초점, 외부 ring, 폼 전체 강조는 실패다. 바깥 컨테이너와 내부 input/textarea가 같은 초점을 중복 강조하지 않는지도 검사한다. 기본 링을 제거했다면 대체 표시의 지속성과 식별성을 확인한다. 입력→전송 Tab 이동 시 실제 대상이 구별되는지, active 해제 후에도 키보드 포커스가 남는지, 오류/고대비에서도 확인한다. 전역 outline:none 또는 pressed 효과만으로 포커스를 대신한 결과는 통과시키지 않는다.

CTA 아이콘 순서: 실제 동작·아이콘 역할·제품 관례·사용자 명시 순서를 기본/로딩/비활성 상태와 대조한다. 선행/후행 자체를 합격 조건으로 삼지 않는다. 정상/누락 상태에서 보이는 묶음의 중심과 빈 슬롯 처리도 확인한다. 모든 버튼에 아이콘을 추가하거나 탐색/필터까지 같은 규칙으로 재배치하지 않는다.

아이콘 기본 출처: React 구현은 lucide-react의 실제 import/사용을, 비 React는 공식 Lucide SVG/해당 환경 패키지와 원본 아이콘 이름을 확인한다. 직접 그린 path나 출처 없는 유사 아이콘을 Lucide로 보고하지 않는다. 명시된 기존 시스템/브랜드에 따른 예외는 범위와 이유를 기록한다. 사용한 아이콘의 의미·역할에 맞는 순서·크기/선/색 일관성도 함께 검사한다.

아이콘 의미 판독: 출처/Lucide 여부와 별개로 이벤트·링크의 실제 동작, 라벨, 아이콘이 암시하는 동작을 대조한다. 예시 입력과 실제 전송에 같은 전송 아이콘을 쓰거나, 이동/복사를 하지 않는데 해당 아이콘으로 대체하면 수정한다. 윤곽선/표면·라벨만으로 충분한 경우 아이콘 생략을 우선 검토한다. 오른쪽 배치와 스타일 통일이 의미 불일치를 정당화하지 않는다(RUI-12).

## 모션 판독

[토큰 계약의 상태 전환과 모션](../../reference-to-ui/references/design-tokens.md#상태-전환과-모션)을 기준으로 hover 진입/해제 양쪽, 빠른 왕복·연속 조작, 터치 pressed, 키보드 포커스, 동작 줄이기를 실제 확인한다. 같은 역할의 속도·곡선이 화면마다 다르거나, 장식 확대·튕김이 반복되거나, 전환 때문에 레이아웃·스크롤·초점이 튀면 수정한다. `transition: all`, hover에만 둔 전환, 애니메이션 종료에 묶인 실제 행동도 확인한다. 정지 캡처와 토큰 선언은 부드러움의 증거가 아니다. 프로젝트 계약에 적용 대상과 제외 효과를 기록하고 기존 게이트의 상태/행동 검증에 연결하며, 미실행은 미검증으로 남긴다.

공통 컨테이너 판독(RUI-22/23): [패딩 소유권](../../reference-to-ui/references/design-tokens.md#공통-화면-컨테이너의-패딩-소유권)에 따라 같은 단계 화면의 기본 inset과 제목/본문/고정 입력창의 최종 기준선을 대조한다. 공통 토큰 사용만으로 통과시키지 않고 부모·자식 여백의 합과 fixed→sticky 전환을 확인한다. 내부 컴포넌트 여백이나 가림 방지 예약 공간까지 같은 숫자로 강제하지 않는다. 예외는 역할과 실제 정렬 근거를 남긴다.

행동 범위와 소속: [행동의 적용 범위와 위치](../../reference-to-ui/references/product-reasoning.md#행동의-적용-범위와-위치)에 따라 실제 변경 대상과 화면/섹션/항목/선택 집합의 배치를 대조한다. 목록 편집을 무관한 날짜 헤더에 놓거나 임시 예시 라벨에만 묶지 않는다. 필터·날짜·선택·빈 상태에서 암시된 대상과 실제 동작이 일치하는지, 편집 종료와 긴 목록에서의 접근성이 유지되는지 확인한다. 계약의 E/D-ID에 소속·표시 조건·잘못된 배치를 제외 항목으로 기록해 기존 게이트의 구조/행동 판독에 포함한다.

행 단위 역할 충돌: 같은 섹션 소속인지 확인한 뒤 각 행의 목적과 행동 우선순위를 따로 판독한다. Todo의 필터 옆에 편집을 동급으로 붙인 결과는 위치 교정 완료로 처리하지 않는다. 조회 행과 목록 요약/관리 영역을 분리하고 임시 예시 표시의 필요성·혼잡도까지 재검토한다. 아이콘/테두리 차이만으로 통과시키지 않는다. 좁은 폭·긴 문구·편집 종료에서 실제 시선 흐름과 조작 구분을 확인하고 계약의 제외 항목과 수정 이력에 보존한다.

사례 일반화 검수: [사례에서 판단 관점으로 일반화](../../reference-to-ui/references/product-reasoning.md#사례에서-판단-관점으로-일반화)에 따라 모든 요소의 필요성·관계·적용 범위·읽기/행동 순서·위계를 판독한다. 특정 버튼 위치나 행 분리 여부 자체를 합격 조건으로 삼지 않는다. 앞선 Todo의 조회/관리 분리는 해당 실패의 해결 후보이며, 원인이 해결됐는지 실제 화면으로 판정한다. 명시적 사용자 요구와 확인된 실패 기록은 유지한다.

경계/포커스 전환: [경계 상태 기준](../../reference-to-ui/references/design-tokens.md#경계-상태와-레이아웃을-흔들지-않는-포커스)에 따라 border-color/inset shadow도 모션 검수에 포함한다. 초점 전후 외곽 크기뿐 아니라 내부 텍스트·줄바꿈·인접 위치를 확인한다. border-box나 inset 선언만으로 통과시키지 않는다. 일반 색상 모드의 입력 초점을 border-color로 대체하지 않는다. 중복 경계, 오류와 초점 충돌, 고대비에서 사라지는 shadow와 대체 표시를 실제 검증한다.

바 금지 재검수(RUI-14): 데스크톱·모바일과 탭 전환 상태를 확인한다. 금지된 선은 단 한 개도 일반적인 탭 관례로 허용하지 않는다. 제거 후 선택 상태를 글자 굵기·적절한 표면 등으로 분명히 표현하고 키보드 포커스는 유지한다. 코드에서 hr 검색만 통과하면 부족하다. 사용자 캡처로 선의 존재는 확인할 수 있지만 구현 속성이나 수정 완료는 실제 코드/렌더 근거가 필요하다.

## 사용자 교정이 있는 목록·선택·내역

[재발 점검](feedback-regression.md)을 함께 읽고 현재 과제에 해당하는 교정을 실제 증거에 연결한다. 저장값/ARIA만으로 토글 표현을 통과시키지 않고, 상태가 붙은 날짜의 형제 치수·셀렉트 커스텀 범위·마지막 시간 접근과 복귀를 확인한다. 다른 뷰에서는 소개/조건/행동, 기간/수량/중복/취소 대상의 의미를 새로 판단한다. 빈 상태/짧은 내용의 스크롤과 정상 긴 내용의 접근을 구별한다. 이전 전체 PASS나 스크린샷 일부로 변경된 사용처의 검증을 대체하지 않는다.
