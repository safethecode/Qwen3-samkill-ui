# 디자인 게이트와 실패 누적

목표는 레퍼런스와 아이디어로 제품의 핵심 과제를 잘 구현하는 것이다. 실패 기준을 통과하는 것만으로 좋은 제품이 완성되지는 않는다. 제품의 행동·정보·상태와 디자인 제외 목록을 모두 판단한다.

일정이나 소요 시간을 이유로 필수 검사 범위·항목·깊이·증거 요건을 축소하지 않는다. 시간 부족을 미적용/예외 사유로 사용하지 않는다. 도구나 자료가 없어 실행하지 못한 검사는 삭제하지 않고 unknown으로 유지한다.

## 기준을 준비하기

1. [실패 목록](failure-catalog.json)의 모든 active ID와 해당 프로젝트의 과거 실패 기록을 읽는다. 원본 규칙을 삭제하거나 ‘취향이니 무시’로 일괄 해제하지 않는다.
2. 각 규칙의 적용 여부·대상 요소/화면·이유를 정한다. 원본 임계값을 사용하는 경우 그대로 기준에 남긴다. 해당하지 않으면 무엇이 없는지/작업 범위가 어떻게 다른지 구체적으로 기록한다.
3. [화면 구성 계약](../../reference-to-ui/references/application-format.md)의 영역·목적지와 실제 페이지를 대조해 검사 범위의 누락부터 확인한다. 구현되어 있는 요소만 검사하면 빠진 영역을 발견하지 못한다. 이번 디자인의 Avoid와 핵심 제품 완료 조건을 `PROJECT-*` 규칙으로 추가한다. 기능 완료를 정적 장식 검사로 대신하지 않는다. 새 아이디어는 의도·해결할 문제·검증 행동을 함께 기록한다.
4. 예외는 범위·이유·사용자 지시/레퍼런스/접근성 근거를 계약에 기록한다. 기존에 명시된 사용자 선택은 다시 승인받지 않는다. 확인 없이 ‘브랜드 예외’라고 붙이거나 모든 규칙을 예외 처리하지 않는다.

원본에는 그라디언트 금지와 미세 그라디언트 제안, 균일 카드와 카드 변형, hover-only와 접근성 요구처럼 충돌할 수 있는 기준이 있다. 서로 충돌하는 ID를 모두 남기고 이번 과제에 어떤 기준을 적용했는지 판단한다. 충돌을 이유로 검사 자체를 없애지 않는다.

## 파일과 검사

기존 프로젝트 경로가 없으면 다음을 사용한다.

- `design/gate-contract.json`: catalog version, 검사할 소스 범위, 전체 규칙의 적용 여부, 프로젝트 제외 목록과 완료 조건, 선언된 예외.
- `design/gate-report.json`: 실제 검사자의 ID별 관찰/판정과 증거.
- `design/failure-events.jsonl`: 실행 결과와 수정/재발을 누적하는 기록. 완료 결과도 기록해 같은 규칙의 실패→해결→재발을 추적한다.

catalog/contract/report의 `schema_version`은 1이다. 계약은 `catalog_version`, `targets`(프로젝트 내부 실제 소스 파일/디렉터리), `rules`를 갖는다. targets는 UI와 토큰에 영향을 주는 범위를 빠짐없이 포함한다. 보고서·증거·누적 기록은 targets 밖에 두어 자기 해시가 자기 자신을 바꾸지 않게 한다.

계약 rule의 필드: `id`, `applicable`(boolean), `scope`, `reason`, `checks`(`spec/code/visual/interaction` 배열), `exceptions`(id·reason, 필요한 범위/근거 추가). 모든 active catalog ID가 있어야 하며 catalog의 checks를 줄일 수 없다. 프로젝트 규칙도 같은 형식을 쓴다.

결과 필드: `id`, `status`(`pass/fail/unknown/exception/not-applicable`), `reason`, `evidence`. 예외 결과에는 선언된 `exception_id`를 쓴다. evidence 항목은 `kind`, `path`(--root 상대 경로), `sha256`이다. `not-applicable`은 계약에서 적용 대상이 아닌 규칙에만 허용한다.

## 실제 판독 순서

설계·구현자는 원본과 출력물을 비교해 **실제로 확인한** 판정을 쓴다. 코드 패턴은 코드와 lint, 외형은 실제 스크린샷, 행동은 실행 기록으로 확인한다. 같은 스타일도 적용 범위와 선언된 예외를 함께 본다. 해결하지 못한 문제는 fail, 확인할 근거가 없으면 unknown이다.

소스가 확정된 시점에 식별 해시를 구한다. `<skill>`은 설치된 reference-review 폴더다.

```sh
python3 <skill>/scripts/design_gate.py fingerprint --root . --contract design/gate-contract.json
```

반환된 `catalog_sha256`, `contract_sha256`, `target_sha256`를 보고서에 복사하고 실제 검사 결과를 `results` 배열에 작성한다. evidence 파일의 SHA-256도 실제 파일에서 계산한다. 해시를 얻었다는 이유로 검사 결과를 미리 pass로 채우지 않는다.

```sh
python3 <skill>/scripts/design_gate.py check --root . --contract design/gate-contract.json --report design/gate-report.json --ledger design/failure-events.jsonl
```

기본 catalog는 설치된 실패 목록이다. `--catalog`는 원본 규칙을 포함한 검토된 통합 catalog나 격리 테스트용으로 사용한다. 더 느슨한 목록으로 바꿔 검사 통과를 만들지 않는다.

- `PASS` / exit 0: 현재 계약의 적용 가능한 규칙을 확인했고 실패·미확인이 없다. 선언된 예외와 미적용 사유는 그대로 공개한다.
- `FAIL` / exit 1: 근거가 있는 실패 결과가 남았다. 수정 후 해당 규칙과 영향 범위를 재검증한다.
- `UNVERIFIED` / exit 2: 누락, unknown, 미선언 예외, 잘못된 증거, 변경된 catalog/계약/소스 등이 있다. 알려진 실패가 함께 있으면 failures 배열도 확인한다.

두 차단 상태는 완료로 승격하지 않는다. 코드 수정 후 이전 화면 캡처를 재사용하거나 해시만 갱신해 과거 판정을 유지하지 않는다. 달라진 범위의 실제 검사를 다시 수행한다. 명세 전용 작업은 아래처럼 산출물 완료와 구현 게이트를 구분한다.

### 명세만 요청된 경우

명세와 검증 계획을 전달하면 `spec-only`로 종료할 수 있다. 구현이나 렌더 실행을 추가로 강제하지 않는다. 명세 산출물의 완료는 구현 게이트 PASS와 별개이며, 구현 게이트는 미실행/미검증이라고 보고한다.

이 단계에서 계약·보고서를 미리 작성한다면 모든 활성 ID와 원래 checks를 유지한다. 예를 들어 RUI-07이 `spec, visual`을 요구하고 배치 이유만 작성했다면 아래와 같이 남긴다. 이 부분 예시만으로 전체 CLI 입력이 완성되는 것은 아니다.

```json
{
  "contract_rule": {"id": "RUI-07", "applicable": true, "scope": "주문 화면 주요 영역", "reason": "사용자 행동에 따라 배치해야 함", "checks": ["spec", "visual"], "exceptions": []},
  "report_result": {"id": "RUI-07", "status": "unknown", "reason": "배치 이유는 명세에 작성했으나 구현 화면이 없어 시각 검사는 미실행", "evidence": []}
}
```

이 상태의 구현 게이트는 UNVERIFIED가 맞다. `visual`을 지우거나 아직 구현하지 않았다는 이유만으로 규칙 전체를 `not-applicable`로 바꾸지 않는다. 미적용은 해당 요소/행동이 실제 작업 범위에 없는 경우에만 사용한다.

이 Python 도구는 **판정의 누락·증거 파일 무결성·검사 시점·규칙 적용·기록을 검증하는 기구**다. 이미지 미관을 자동 인식하거나 검사자의 관찰이 사실인지 증명하지 않는다. visual로 지정한 파일이 있다는 사실만으로 이미지 판독을 했다고 주장하지 않는다. 원본/구현 화면을 직접 비교하는 단계는 필수다. Python 3의 Unix 환경에서 동작하며 외부 패키지가 필요 없다.

## 계속 누적하고 학습하기

`--ledger`는 결과 전체를 덮어쓰지 않고 새 실행을 한 줄씩 추가한다. 같은 입력과 결과의 반복 실행은 중복 저장하지 않는다. 과거 실패를 지우거나 pass로 바꿔 쓰지 않는다. 증거 파일도 실행별 이름으로 보존한다.

다음 작업 시작 시 같은 화면/컴포넌트/토큰/규칙의 과거 fail·unknown·예외와 이후 결과를 읽는다. 같은 문제가 다시 나타나면 같은 ID로 기록한다. 신규 실패는 `PROJECT-*` ID로 정의하고 `발생 조건 → 관찰 증거 → 영향 → 원인 가설 → 수정 → 재검증`을 결과 reason 또는 별도 증거 문서에 남긴다. 확인 전 원인 가설을 확정 사실로 쓰지 않는다.

다른 작업에도 적용할 수 있는 실패는 공통 catalog 후보로 정리한다. **한 번의 실제 실패도 기록**하고, 재현 가능한 조건·반례·수정 검증이 있으면 공통 규칙으로 승격한다. 반복 횟수만으로 무조건 일반화하지 않는다. 공통 목록을 관리할 수 있는 작업에서 원본 규칙을 보존하며 새 ID를 추가하고 version을 올린다. 단발성 조건은 프로젝트 범위에 둔다. 쓰기 권한이 없으면 후보를 프로젝트 기록에 보존한다.

규칙이 잘못됐다고 드러나면 삭제 대신 deprecated 상태와 사유·대체 ID를 기록한다. 새 catalog는 기존 해시와 달라져 과거 PASS를 재사용할 수 없다. 재발한 사례는 회귀 평가 입력에도 추가한다. 판독 기준과 제품의 디자인 품질을 함께 발전시킨다.

## 결과 파일과 완료 보고의 일치

CLI를 실행한 작업 디렉터리와 --root/--contract/--report 경로를 확인한다. 경로 오류로 UNVERIFIED가 나왔으면 보고서 문장으로 PASS를 대신하지 말고 경로를 고쳐 실제 재실행 결과를 확인한다. 최종 저장된 결과의 status/해시/종료 코드와 리뷰 총괄이 모순되지 않아야 한다. 과거 aligned 문서는 새 사용자 교정이나 새 catalog의 검증을 대체하지 못한다.

제품 구성 누락을 사용자에게 지적받으면 기존 PASS의 범위 밖이었던 조건과 놓친 검토를 기록하고 프로젝트 완료 조건에 연결한다. 기존 성공 기록을 삭제하지 않으며 새 조건의 구현·판독·행동 근거를 확보한다. 공통 규칙 개수나 증거 해시가 일치한다는 이유로 제품에 필요한 영역과 흐름이 충분하다고 판단하지 않는다.
