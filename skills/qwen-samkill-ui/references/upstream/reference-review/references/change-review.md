# 변경 전후와 공통 원인 리뷰

브랜치·PR·커밋·작업 중 변경을 리뷰하거나 공통 토큰/컴포넌트 수정의 영향을 확인할 때 읽는다. 화면 전체 리뷰와 변경 귀속 판단을 구별한다. 기존 `V-ID`, 심각도, 상태, 게이트를 그대로 사용하고 새 승인 체계를 만들지 않는다.

## 비교 범위

사용자가 지정한 대상과 base/head의 실제 revision, 포함한 staged/unstaged/untracked 범위를 남긴다. 작업 트리가 깨끗하다는 이유로 마지막 커밋을 임의 대상으로 삼지 않는다. 비교 대상이 없으면 그 사실과 필요한 대상을 설명한다. 현재 화면 리뷰를 요청한 경우에는 diff가 없어도 진행한다.

변경 파일은 출발점이다. 공유 CSS·토큰·컴포넌트의 정의→참조→실제 소비 화면을 추적하고 해당 상태·viewport까지 펼친다. 일정한 파일 수나 import 두 단계로 검사 범위를 잘라 전체 확인이라고 하지 않는다. 빌드 산출물은 소스 리뷰의 중복일 수 있지만 실제 배포/진입이 번들을 사용하면 그 경로의 실행 검증은 유지한다.

## 삭제한 신호와 대체 구현

추가 줄뿐 아니라 삭제 줄에서 label/ARIA, focus, 오류/선택 표현, 줄바꿈, 토큰, 언어 방향, 동작 줄이기, 복구 문구가 사라졌는지 확인한다. 이름이 사라졌다는 것과 기능이 사라졌다는 것을 구별한다. 예를 들어 `aria-label`을 보이는 제목의 `aria-labelledby`로 바꾸거나 `div role=button`을 실제 button으로 바꾸면 동등한 동작을 확인한 뒤 회귀 여부를 결정한다.

V-ID의 발생 구분은 아래 중 하나로 기록한다. 이 값은 기존 리뷰 상태나 게이트의 fail/unknown을 대체하지 않는다.

- `introduced`: 변경이 새 문제를 만듦.
- `regression`: 이전에 되던 표현·기능을 약화함.
- `pre-existing`: 변경 전에도 동일 문제였음.
- `origin-unverified`: 이전 증거가 부족해 발생 시점을 확정하지 못함. 현재 재현된 결함까지 unknown으로 바꾸지 않음.

수정하지 않은 줄도 공유 토큰 변경의 영향을 받으면 이번 변경에 의한 회귀일 수 있다. 위치가 diff 근처라는 이유만으로 신규 결함으로 분류하지 않고 실제 원인과 양쪽 결과를 대조한다.

## 원인 하나와 여러 사용처

공통 토큰 하나로 여러 화면의 대비가 깨지면 원인을 한 V-ID로 묶고 확인한 사용처·상태·차이를 모두 연결한다. 근거는 코드 위치/selector, 전후 실제 화면, 행동 결과 중 해당 판단에 필요한 종류를 쓴다. 서로 다른 원인의 문제를 같은 증상이라는 이유로 합치지 않는다.

수정은 기존 시스템 안에서 가장 작은 충분한 변경을 선택한다. 삭제하면 의미·상태·접근성을 잃는 경우 삭제가 가장 작은 해결책이 아니다. 공유 원인을 고쳤다면 대표 한 곳의 캡처만으로 영향받은 모든 사용처를 통과시키지 않는다.

## 변경 귀속과 제품 게이트

변경 리뷰는 이번 수정의 책임 범위를 설명한다. 제품 게이트는 현재 적용되는 모든 실패 기준을 판정한다. `pre-existing`이라고 현재 키보드 결함을 해제하거나 이전 PASS를 재사용하지 않는다. 짧은 보고서는 가능하지만 전체 판독 기록에서 결함·필수 검사·미검증을 숨기지 않는다.
