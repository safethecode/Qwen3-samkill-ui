# 레퍼런스 기반 UI 리뷰

레퍼런스와 아이디어가 제품의 핵심 과제를 좋은 디자인으로 구현했는지 판단한다. 실제 차이와 사용자 영향을 기록하고 실패를 누적한다. 취향 점수나 AI 생성 주체 판별로 대체하지 않는다.

## 입력과 범위

사용자 과제, 레퍼런스/관찰 기록, 적용 계약, 구현 화면/코드, 목표 뷰포트를 확인한다. 이미 있는 자료를 재사용한다. 리뷰만 요청하면 코드 수정·배포·외부 전송을 하지 않는다. 수정을 요청받았다면 중요한 차이를 고치고 해당 항목을 재검증한다.

계약이 없으면 사용자 요구와 제공된 관찰에서 최소 비교 기준을 만들고 reviewer-derived로 표시한다. 직접 본 이미지, 전달 관찰, 구현 설명, 코드 검사, 행동 실행의 근거 종류를 구분한다. 설명만 있어도 우려와 확인 계획은 작성하되 시각 검증 통과 판정은 하지 않는다.

대상 루트 `DESIGN.md`와 연결된 토큰·계약을 먼저 읽고 실제 구현에 반영됐는지 검사한다. 문서 누락·오래된 값·기준 충돌을 기록한다. 리뷰만 요청되면 수정하지 않으며, 작성/수정 권한이 있으면 `design-md`로 분석·갱신한다. 루트 문서 존재나 형식 통과가 구현 품질 통과를 뜻하지 않는다.

## 검사

브랜치/PR/작업 중 변경이나 공유 토큰의 영향 검토는 [변경 전후 리뷰](references/change-review.md)를 읽고 삭제된 신호·동등한 대체·전체 소비 화면을 추적한다. 발생 구분과 현재 제품 게이트를 구별한다. AI 스타일 정리/외부 스캐너 결과는 [탐지 결과 판독](references/deslop-triage.md)으로 후보를 실제 근거에 연결한다.

글자·폰트·잘림은 [타이포그래피](../reference-to-ui/references/typography.md), 폼·비동기·상태 조합은 [내용 경계와 연속 상태 검증](references/state-stress.md)을 적용한다. 정적 표본의 외형과 실제 소비 화면·전이·보조 기술 실행 결과를 나누어 기록한다.

사용자 교정이 누적된 UI나 같은 패턴의 다른 화면을 검토할 때 [사용자 교정의 재발 점검](references/feedback-regression.md)을 읽는다. 관련 피드백을 기존 규칙·실제 사용처·상태별 증거에 연결하고 이전 수정이 만든 새로운 위계/중복/스크롤 문제까지 확인한다.

프롬프트 기반 재현 실험은 [reference-decompose](../reference-decompose/guide.md)의 입력 버전·E-ID·독립 표본·조립 결과를 대조한다. 차이가 번역 누락/오독인지 구현 불이행인지 나누며, 사용자 교정과 내부 발견을 구분해 수정 프롬프트와 재렌더 증거를 보존한다.

여러 화면을 확장하기 전에도 [핵심 화면의 첫 비교](../reference-to-ui/references/reference-synthesis.md#핵심-화면의-첫-비교)를 수행한다. ‘레퍼런스를 반영했다’는 주장마다 원본 영역과 결과의 대응 영역을 직접 대조한다. 구조·위계·밀도가 사라졌다면 출처 목록, 일부 색/사진의 유사성, 작성한 계약만으로 통과시키지 않는다. 핵심 퇴보를 수정·재검증한 뒤 의존 화면을 확장하고 마지막에는 전체 조합을 다시 검사한다. 형식·범위의 명시 요청을 보존하며 별도 사용자 승인 절차를 만들지 않는다.

검사 상태는 항목별 실제 근거로 기록한다. 게이트 항목에서 이미 확인한 실패는 fail로 유지하고, 실행하지 않은 검사는 unknown 사유와 다음 실행을 남긴다. Q-ID의 비교 판정, V-ID의 리뷰 상태, 게이트 항목 상태는 구별한다. 수행 가능한 검사·수정이 남았는데 모든 항목을 일괄 unknown으로 채워 종료하지 않는다. API·인증·도구 제한은 실제 의존 항목에만 적용하고 독립적인 로컬 렌더·문구·토큰·시각 비교는 계속한다. 읽기 전용 검토에서는 수정안과 검증 범위까지 전달하며 제품을 임의로 변경하지 않는다.

복합 제품의 B-ID별 검색·출처·D/Q 적용을 확인한다(RUI-18). 채팅만 조사하고 Todo 목록을 빠뜨리거나, 여러 호출 결과 중 마지막 출처만 구현했으면 조사/적용 완료로 판정하지 않는다. 모바일 탭은 RUI-19에 따라 CTA와 다른 내비게이션 구조·선택 표시·공간 비율을 비교한다.

[레퍼런스 결합 품질](../reference-to-ui/references/reference-synthesis.md)을 읽고 Q-ID별 원본/구현을 나란히 비교한다. RUI-16/17의 긍정 기준(장점의 실제 유지와 전체 조합 품질)을 제외 목록 검사와 별도로 판독한다. 핵심 특징의 퇴보를 ‘의도적 차이’라는 이름만으로 통과시키지 않는다.

[UI 구성 기준](../reference-to-ui/references/ui-composition.md)을 읽고 RUI-08–15와 RUI-20–23을 실제 화면/코드/행동과 대조한다. 생성 폼의 주 제목·선택형 입력, 부모/자식 여백과 화면 간 톤을 포함한다. 로고에 실제 요청 근거가 있는지, 기본14px와 선언·검증된 보조정보12px 예외, CTA와 필터의 구분, 문구의 필요 위치, 아이콘 출처·의미, 반복 구분선, 소수 항목 스크롤, 목록/채팅 전환을 검사한다. 구현자가 쓴 ‘브랜드’, ‘가독성’, ‘주 콘텐츠라 스크롤 허용’이라는 설명만으로 통과시키지 않는다.

[디자인 게이트와 실패 누적](references/design-gate.md)을 반드시 읽는다. 공통 실패 catalog의 모든 active 규칙과 프로젝트 과거 기록을 검토하고 적용 범위·제외 목록·제품 완료 조건을 계약에 연결한다. 실패 기준을 ‘결함이 아닐 수도 있음’으로 삭제하지 않고, 미적용/예외가 필요하면 근거와 범위를 남긴다.

[리뷰 기준](references/review-criteria.md)을 읽는다. 실제 구현을 렌더링해서 레퍼런스와 같은 너비·가능하면 같은 높이/상태로 확인한다. 원본 뷰포트 미상은 남긴다. **구조/핵심 과제 → 위계/밀도 → 글자/콘텐츠 → 색/표면 → 상태/행동** 순서로 검사한다.

E-ID 상세 기록과 토큰 계약을 함께 대조한다. 사방 여백·버튼 배경과 글자/아이콘 조합·아이콘 선/채움/정렬을 확인하고, 토큰 정의 → 참조 → 사용처와 직접값 예외를 코드에서 검사한다. 토큰 파일 존재만으로 토큰화 완료를 판정하지 않는다.

중요 행동은 실제로 실행한다. 정지 화면으로 hover·focus·스크롤 고정·복구를 확인했다고 하지 않는다. 빌드·테스트 결과는 해당 검증에만 사용한다. 미실행 검사는 `not-verified`다.

Do/Avoid와 의도적 차이를 함께 비교한다. 사용자 지정 그라디언트나 이미지 중심 카드가 있다는 이유로 결함을 만들지 않는다. 구조가 틀렸다면 색상만 고쳐서 해결했다고 하지 않는다. 차이가 몇 개라는 이유로 전면 재작성하지 않는다.

## 결과 계약

기존 리뷰 문서 또는 `design/review.md`에 다음을 남긴다. 짧은 리뷰는 채팅으로 충분하다.

- 검증 범위: 자료/출처, 확인한 뷰포트·상태, 도구 실행, 미확인 범위.
- 항목별 V-ID, 관련 D/O-ID, 근거 종류, 예상/실제 차이, 사용자 영향, 심각도, 최소 수정, 재검증 방법, 상태.
- 상태는 `confirmed / suspected / fixed-and-verified / not-verified / accepted-difference` 중 실제 근거에 맞게 쓴다.
- 총괄은 `aligned / changes-needed / not-verified`. 핵심 시각 검사가 미실행이면 총괄은 not-verified이고 설명 기반 우려를 별도로 적는다. aligned도 실제 확인한 범위에 한정한다.

## 우선순위와 종료

최종 완료 전에 design_gate.py로 계약/보고서/증거를 검사하고 `--ledger`로 결과를 누적한다. FAIL/UNVERIFIED는 완료로 표시하지 않는다. 대상 소스가 바뀌면 영향 범위를 재검사한다. 명세/코드/시각/행동 검증 범위를 구분한다. 도구의 PASS는 실제 판독 기록의 검증이며 자동 미관 판별이 아니다.

P0: 핵심 행동 실패·정보 손실 등 현재 작업을 막는 문제. P1: 구조·위계·밀도 또는 주요 상태가 과제를 크게 방해. P2: 사용을 막지 않는 국소 시각 차이. 미확인 위험을 확인된 P0 결함으로 과장하지 않는다.

완료 시 고친 사항과 남은 사항을 구분하고 실제 근거 경로를 제공한다. 리뷰 완료와 제품 출시 가능은 다르다. 검증하지 않은 기능·보안·데이터까지 출시 승인했다고 말하지 않는다. 일정이나 시간 부족을 가정해 검사 범위·항목·깊이·통과 기준을 줄이지 않는다. 정해진 필수 검사를 모두 수행한다. 실행할 수 없는 검사는 필수 항목으로 유지하고 미검증 사유를 기록하며, 검증을 완료할 때까지 통과로 판정하지 않는다.
