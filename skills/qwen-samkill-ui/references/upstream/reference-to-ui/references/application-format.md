# 적용 계약

루트 `DESIGN.md`를 먼저 읽고 현재 기준의 진입점으로 유지한다. 작성/갱신은 `design-md`의 분석 흐름을 따른다. 상세 계약은 기존 문서 구조를 우선하며 기본 경로는 `design/design-contract.md`다. 루트에서 이 계약을 연결하고 값과 근거를 중복 관리하지 않는다. 각 결정은 관찰 R/O-ID 또는 사용자 요구에서 출발한다. 사용자 관찰 기록을 인계받았다면 직접 관찰했다고 바꾸지 않는다.

## 필수 항목

- 구체적인 사용자·문제·핵심 행동과 성공 상태. 중요한 E-ID의 정보·배치·강조 이유.
- 레퍼런스의 원리/시각 문법과 새 아이디어의 역할·기대 효과·검증. 제품 고유 목적에 맞춘 결합.
- [Q-ID 대응표](reference-synthesis.md): 원본 영역의 구체 장점 → 유지할 관계/변경 이유 → 구현 요소·토큰 → 원본/구현 나란히 비교 → 유지·검증된 변형·퇴보·미검증.

- 과제와 우선 행동, 대상 뷰포트, 브랜드/기존 토큰, 주 레퍼런스와 보조 역할.
- 복합 제품의 B-ID별 SC/R 출처 누적과 D/Q 구현 연결. 핵심 분기의 부족한 자료와 후속 검색.
- 화면 구성 범위: 진입 → 핵심 내용/행동 → 마지막 영역 → 다음 목적지. 각 영역의 역할·실제 연결·생략 근거를 적는다. 랜딩은 아래의 조건부 계약을 적용한다.
- 화면별 주 제목/라벨 역할, 선택형 입력 변형, 부모/자식·상태별 간격 합, 화면 간 동일 역할 비교와 의미가 중복된 정보 제거.
- 요소별 역할(탐색/필터/실행), 필요한 문구와 삭제 이유, 브랜드/아이콘의 실제 요청·자산 출처.
- 목록/대화 등 과제별 화면 구성 선택과 대안, 초안/선택 상태 보존, 빈·소수·긴 내용의 스크롤 영역과 검증.
- Do: 보존할 구조와 정보 위계.
- Avoid: 넣지 않을 구체 요소 + 근거 + 대안.
- Intentional differences: 원본과 다르게 구현할 부분 + 요구/접근성/브랜드 근거.
- Unknown: 미확인 관찰, API 의존성, 임시 결정.
- 요소 E-ID의 박스·사방 여백·타이포그래피·버튼 배경/글자/아이콘/테두리와 상태별 조합. 원본값/추정값과 채택한 CSS 값을 분리한다.
- [디자인 토큰 계약](design-tokens.md)의 이름·역할·값/별칭·출처·실제 사용처 표. 직접값 예외와 테마/상태 범위를 포함한다.
- 공통 실패 ID와 프로젝트 제외 목록, 미적용/예외 근거, 과거 재발 사례, 디자인 게이트와 핵심 제품 완료 조건.

| 결정 ID | 근거/출처 종류 | 적용 규칙·값 | 구현 대상 | 시각 기준 | 행동/상태 기준 |
|---|---|---|---|---|---|
| D1 | 사용자 제공 R1/O1: 데스크톱 1440 너비에서 주문 20행 관찰 | 상단 필터 + 정렬된 주문 표. 행 밀도는 내용과 접근성을 보존하며 목표 화면에서 비교 | OrdersPage/OrdersTable (예정 이름) | 같은 viewport 높이도 확인하고 visible rows·필터 위치 비교; 높이 미상은 정확한 행 수 보장 금지 | 선택/부분 선택/필터 변경 정책 확인 |
| D2 | R1/O2: 작은 반경으로 보임, estimated | 반경 시작값 4px chosen; 기존 토큰 있으면 우선 비교 | surface 토큰 | 원본과 나란히 표면 비교 | 포커스 표시가 잘리지 않음 |
| D3 | 사용자 브랜드 요구 | 기존 보라색과 gradient CTA 유지. 토큰 조회 전 값 unknown, 실제 토큰을 확인한 뒤 existing-token | PrimaryAction | 텍스트 가독성과 주요 행동 위계 | focus/disabled/loading 구분 |

예시는 가상 주문 관리 명세다. 관찰된 너비만으로 전체 뷰포트 높이·행 높이를 역산하지 않는다. 코드베이스가 없다면 대상 이름은 예정임을 표시한다. 픽셀 재현 요구가 없으면 본질적인 위계·작업 적합성을 먼저 비교한다.

## 인계

구현 파일이 생기면 예정 이름을 실제 파일/컴포넌트로 갱신하고 결정 ID는 유지한다. 검토자는 D-ID에 V-ID 검사 결과를 붙인다. 수정 사유와 검증 결과를 바꾸어도 원본 관찰을 덮어쓰지 않는다.

## 랜딩과 연결된 도구의 구성 계약

랜딩 제작 요청에서는 첫 화면뿐 아니라 페이지 끝의 탐색과 서비스 정보까지 설계 범위에 둔다. 계약에 `영역 | 사용자 질문/행동 | 실제 내용·목적지 | 검증 상태`를 작성한다. 푸터에는 서비스 식별, 필요한 주요 경로와 이용 정보를 제품 규모에 맞게 배치한다. 짧은 캠페인처럼 간단한 마무리로 충분하면 해당 목적을 기록한다. 열 수·메뉴 수·회사 정보·약관의 일률적 추가는 요구하지 않는다. 확정되지 않은 사업자·연락처·정책은 만들지 않으며 연결 없는 링크로 완성된 척하지 않는다.

소개에서 약속한 기능은 실제 도구의 행동과 대응시킨다. 고정된 문서 예시/시뮬레이션은 실제 사용자 데이터·자동 생성 결과와 구별한다. 새 작성과 기존 작업 열기가 함께 있으면 문서 생성 여부·기존 상태 보존을 각각 검증한다. 진입점을 옮길 때에는 저장 범위와 새로고침/재진입을 확인한다. 직접 파일 실행은 제공하기로 한 제품에서 검사하며 서버 필수 제품까지 변환하지 않는다.

푸터의 존재 여부만 확인하지 않는다. 페이지 끝까지 읽은 상태에서 필요한 목적지로 이동하고, 좁은 폭·글자 확대·키보드에서 링크와 마지막 내용에 접근하는지 확인한다. 편집기·모바일 앱·몰입형 작업 화면은 그 작업의 탐색과 종료 흐름으로 판단하며 마케팅 푸터를 복제하지 않는다.
