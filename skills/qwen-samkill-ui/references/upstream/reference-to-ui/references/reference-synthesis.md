# 레퍼런스의 장점을 구현 품질로 연결하기

사용자가 레퍼런스로 디자인하거나 여러 장점을 결합해 달라고 하면 반드시 읽는다. 목표는 레퍼런스에서 좋은 부분을 구체적으로 가져와 제품에 맞는 하나의 화면으로 완성하는 것이다. 출처와 채택 이유를 적었다는 사실만으로 반영 완료가 아니다.

## 무엇이 좋은지 먼저 특정하기

각 후보를 실제 이미지로 확인하고 과제에 도움이 되는 장점을 영역 단위로 설명한다. ‘깔끔함’, ‘세련됨’, ‘날짜 선택 있음’처럼 어디서나 쓸 수 있는 평가는 부족하다. 예를 들어 제목/메타데이터의 대비, 체크와 텍스트의 정렬, 행 사이와 그룹 사이의 다른 간격, 선택 상태가 주 행동을 압도하지 않는 크기, 입력과 결과의 연결처럼 눈으로 대조할 특징을 기록한다.

기능 패턴과 시각 표현을 함께 가져온다. 체크 옆에 제목이 있다는 기능만 채택한 뒤 표면·간격·밀도·타이포그래피를 전부 기본값으로 바꾸면 원본의 장점을 잃을 수 있다. CSS 원본값이 unknown이어도 관찰한 비율과 관계는 남길 수 있다. unknown을 핑계로 모든 값을 임의 chosen으로 바꾸지 않는다.

현재 과제에 적절한 품질의 후보가 없으면 검색을 좁혀 보완한다. 첫 결과 몇 개를 반드시 사용하는 것이 아니다. 예를 들어 Todo 날짜 화면은 대화 흐름의 레퍼런스가 아니다. 지속적인 채팅이 필요한데 목록 자료만 있으면 적절한 대화 입력·결과·전환 자료를 추가로 확인하거나 그 부분은 신규 설계/미검증임을 밝힌다. 이미 충분한 자료는 다시 검색하지 않는다.

## 조합하기 전에 역할과 충돌 결정

주 레퍼런스는 화면 전체의 위계·밀도·시각 규칙을 잡는 기준으로 사용한다. 보조 레퍼런스에서는 우리 과제에 더 적합한 컴포넌트나 흐름을 가져온다. 여러 레퍼런스의 좋은 부분이 있으면 사용하되 개수를 채우거나 각각의 브랜드 스타일을 그대로 붙이지 않는다.

[화면 스타일 계약](../../reference-decompose/references/element-contract.md#각색-전-화면-스타일-계약)으로 색·표면·그림·간격의 관계를 먼저 정리한다. 조합의 공통 값은 이 관계를 구현하는 선택이며, 원본 HEX 복사나 익숙한 팔레트 선택 자체를 채택 근거로 삼지 않는다.

각 채택 요소에 다음 표를 남긴다. 같은 역할의 반복 요소는 묶는다.

`Q-ID | 출처 R/O/E-ID와 이미지 영역 | 가져올 구체 장점 | 유지할 시각 관계/구조 | 우리 제품에서 바꿀 부분과 이유 | 구현 요소/토큰 | 실제 비교 증거 | 판정`.

색·글꼴·선·반경·아이콘·간격을 공통 규칙으로 조정하되 장점의 핵심까지 없애지 않는다. 보조 컴포넌트를 가져온 뒤 이질적인 밀도나 위계가 생기면 조합을 다시 선택한다. 새 아이디어에는 해결할 마찰과 실제 확인할 행동을 붙인다.

## 무엇을 보존하고 무엇을 바꾸는가

- 관찰된 **핵심 특징**은 완료 시 실제 구현에서 확인해야 한다. 제품 과제에 맞지 않으면 대체안이 같은 목적을 어떻게 달성하는지 비교한다.
- 사용자 명시 기준(예: 기본14px/검증된 보조정보12px 예외, 임의 로고/구분선 금지)은 원본보다 우선한다. 글자를 키웠으면 주변 간격·행 높이·노출 내용도 함께 조정해 읽기 리듬과 밀도를 보존한다.
- ‘카드는 AI스럽다’, ‘무조건 단색’ 같은 일반론으로 원본의 그룹 구조를 전부 지우지 않는다. 실패 규칙과 충돌하는 요소는 규칙 ID·적용 범위·사용자 요구·검증을 기록하고 적절한 다른 레퍼런스나 표현으로 대체한다.
- 바꾼 것을 모두 ‘의도적 차이’로 적어 닮지 않은 결과를 정당화하지 않는다. 차이의 이유와 결과가 좋아졌다는 근거는 서로 다르다. 비교하지 못했으면 미검증이다.

## 핵심 화면의 첫 비교

여러 화면을 새로 설계하거나 구조를 바꾸는 작업에서는 사용자 핵심 행동과 공통 시각 규칙을 가장 잘 드러내는 화면 하나를 먼저 만든다. 단순 문구 수정처럼 구조에 영향이 없는 작업은 변경 영역을 비교 대상으로 삼는다. 특정 사례의 지도 배치·색·사진 위치를 모든 제품에 복제하지 않는다.

1. 주 레퍼런스의 원본 영역과 반드시 유지할 관계를 Q-ID에 연결한다. 읽기 순서, 영역 간 비중, 행/그룹 밀도, 사진과 글자의 비율, 주 행동의 강조처럼 결과에서 식별할 특징을 선택한다. 개수를 채우거나 추정치를 정확한 CSS 값으로 만들지 않는다.
2. 실제 길이의 내용과 필요한 기본 상태로 첫 화면을 렌더한다. 원본 전체/핵심 영역과 결과를 같은 표시 폭으로 나란히 직접 확인하고 비교 증거를 남긴다. 원본 viewport/DPR가 미상이면 표시 폭만 맞췄음을 명시한다.
3. 각 핵심 특징을 아래 Q-ID 판정으로 평가한다. 큰 사진·카드·여백이 원본의 정보 관계나 밀도를 밀어냈다면 색상·출처 수가 같아도 퇴보다. 사용자 요구로 바꾼 부분은 원래 목적을 어떻게 보존했는지 결과에서 확인한다.
4. 핵심 `regressed`는 수정·재렌더·재비교한 뒤 그 구조에 의존하는 화면으로 확장한다. 관찰 근거가 부족한 핵심 `unverified`는 필요한 자료/검사를 확보한다. 실제 접근·도구 제한이 있으면 해당 범위와 이유를 남기고 독립적으로 가능한 작업을 진행하며, 비교 완료나 전체 구현 완료로 표시하지 않는다.

첫 비교가 끝나도 마지막의 전체 화면·상태·상호작용 검사를 생략하지 않는다. 이미 확인한 실패를 unknown으로 바꾸거나 ‘추가 확인 필요’라는 기록만 남겨 수행 가능한 수정·검사를 끝내지 않는다. 외부 API 부재는 그 API에 의존하는 행동의 제한이며 로컬 렌더·토큰·문구·정렬 검사의 중단 사유가 아니다. 명세 전용/읽기 전용 요청에서는 유지할 특징과 비교 계획만 인계하며, 이미지 시안 요청에서는 시각 비교와 실제 CSS·행동 검증을 구별한다.

## 실제 화면으로 긍정 기준을 검증

### 결정이 갈릴 때의 대안 비교

사용자가 대안을 요청했거나 핵심 배치 결정에 비교가 필요하면 한 판단 축을 먼저 정한다. 예를 들어 목록의 밀도, 주 행동의 강조, 정보 묶음 순서 중 무엇을 비교하는지 쓰고 같은 실제 내용·기능·주변 화면에서 대안을 렌더한다. 색만 바꾼 후보나 모든 축을 동시에 바꾼 후보로 원인을 흐리지 않는다. 명시적으로 색을 비교하는 요청에서는 색 역할/대비를 비교 축으로 삼을 수 있다.

`후보 | 바꾼 축/가설 | 유지한 Q-ID 관계 | 유리한 과제 | 비용 | 실제 비교`를 남긴다. 후보 수를 채우려고 기존 브랜드를 다시 만들거나 읽기 크기·키보드·상태 의미를 타협하지 않는다. 미리보기 선택기는 개발 표본이며 출시 화면의 UI로 남기지 않는다. 사용자가 선택을 요청하면 비교 결과를 전달하고, 구현을 위임했다면 근거로 결정해 진행한다. 핵심 첫 화면 비교와 최종 게이트는 그대로 수행한다. [Jakub variant](https://github.com/jakubkrehel/skills/tree/267330e1adfc66a718fb65fa6918c1f06d0a689e/skills/variant)의 단일 축·실제 맥락 비교를 적용하되 세 후보·중립 팔레트·매번 사용자 선택을 강제하지 않는다.

### 원본과 결과 판독

구현 후 원본과 결과를 나란히 보고 Q-ID별로 검토한다. 원본 전체와 핵심 컴포넌트, 구현 전체와 같은 역할의 컴포넌트가 대응돼야 한다. 원본 CSS viewport/DPR가 미상이면 표시 폭을 맞춘 정지 비교라는 점을 밝히고 정확한 px 일치를 주장하지 않는다. 실제 구현 viewport·상태·데이터 길이도 남긴다.

비교할 것은 정보 위계, 화면 내 작업 공간 비율, 밀도와 간격 리듬, 글자 위계·줄바꿈, 색/표면, 버튼·아이콘 표현, 정렬, 콘텐츠 완성도다. 행동 품질은 실제 전송/선택/전환/복귀 실행으로 따로 확인한다. 일부 색·pill·날짜 선택이 같다는 이유로 전체 품질을 통과시키지 않는다.

Q-ID 판정은 `retained / adapted-and-verified / regressed / unverified`로 기록한다. 핵심 채택 장점이 사라졌거나 원본 대비 정렬·위계·밀도가 무너지면 regressed다. 근거 없이 ‘동급’, ‘세련됨’, ‘aligned’라고 적지 않는다. 합성 결과 전체에 스타일 충돌·과도한 공간 경쟁이 없는지도 별도로 확인한다. 전체 화면의 시선 순서·강조 면적·그림 표현·그룹 경계가 유지되는지 먼저 판독하고 요소별 비교를 연결한다. 기능 소속이나 일부 간격만 맞는 부분 판정을 전체 스타일 통과로 확대하지 않는다. 사용자가 느낌·스타일 손실을 지적하면 이전 판정의 범위를 교정하고 실제 실패를 보존한다.

RUI-16은 채택 특징의 실제 반영, RUI-17은 조합 결과의 전체 품질과 근거를 판독한다. 관련 규칙이 적용되면 Q-ID 표와 나란히 비교한 증거가 필요하다. 핵심 regressed를 고치고 영향 범위를 다시 비교한다. 자료가 없으면 unverified다. 제외 목록 통과로 이 검사를 대신하거나 보기 좋은 원본 캡처만 보고 구현도 좋다고 판단하지 않는다.

## 이번 Todo 실패에서 배울 점

기존 brief에는 레퍼런스의 날짜·체크·표면·간격을 관찰한 기록이 있지만, 계약에서 거의 모두 chosen 값과 새로운 단일 목록/채팅 구조로 바뀌었다. 기존 리뷰는 기능과 제외 항목을 확인했으나 원본의 좋은 시각 관계가 최종 화면에 남았다는 Q-ID별 비교 근거가 부족하다. 이는 현재 문서 대조로 확인한 인계·판독의 공백이다. 이 문서만으로 원본 이미지와 구현의 정확한 차이를 새로 측정했다고 주장하지 않는다.

이를 고칠 때 예전 레퍼런스를 무조건 그대로 복사하지 않는다. 목록과 대화에 적절한 장점을 다시 선정하고, 하나의 시각 규칙으로 결합한 뒤 실제 화면 비교에서 유지·변형·퇴보를 판단한다.
