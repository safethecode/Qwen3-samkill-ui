# 요소를 덜고 행동을 구분하는 UI 구성

UI 설계·구현 전에 읽는다. 사용자가 Todo 테스트 결과에서 직접 지적한 실패를 반영한 기본 기준이다. 단어만 바꾸거나 숫자를 토큰에 넣는 것으로 통과하지 않는다. 실제 화면에서 정보의 필요성과 행동의 구분을 확인한다.

## 레이아웃의 전환 조건과 읽기 순서

컴포넌트가 넓은 본문과 좁은 사이드 패널에서 함께 쓰이면 viewport뿐 아니라 실제 가용 폭에서 구조를 판단한다. 기존 breakpoints를 먼저 확인하고 긴 내용·형제 압축·확대에서 무엇이 먼저 깨지는지 기록한다. 필요하면 container query를 검토하되 기존 시스템을 일괄 전환하지 않는다. 레이아웃이 깨지는 폭의 바로 전후를 실제로 비교하고 충분히 들어가는 구조를 기기 이름만으로 조기에 접지 않는다.

시각 순서와 DOM/키보드 읽기 순서를 함께 대조한다. CSS order나 grid 재배치로 화면의 다음 항목과 Tab의 다음 대상이 달라지지 않게 한다. RTL을 지원하면 논리적 시작/끝과 물리적 화면 가장자리를 구별하며 숫자·데이터 순서를 임의로 뒤집지 않는다.

접힌 보조 정보와 화면 밖으로 이어지는 콘텐츠에는 실제 펼침/넘김 단서가 있어야 한다. 단서는 현재 남은 내용과 일치해야 하며 모든 콘텐츠를 숨기거나 항상 ‘더 보기’를 추가하지 않는다. 단순 개수 기준으로 행동을 메뉴에 넣지 말고 빈도·중요도·비교 필요성을 판단한다. 중요한 조건·오류·행동은 노출과 접근을 유지한다.

상하/좌우 기준선, 내부·외부 간격과 계층은 기존 토큰·실제 관계로 정한다. 그룹 간격을 항상 두 배, 아이콘 사이를 항상24px로 고정하지 않는다. 다른 선택을 했다면 관련 실패 규칙의 예외·검증을 남긴다. 좁은 폭·키보드·고정 영역에서 마지막 내용과 행동에 도달하는지 확인한다. 이 보완은 [Jakub grouping-and-alignment](https://github.com/jakubkrehel/skills/blob/267330e1adfc66a718fb65fa6918c1f06d0a689e/skills/better-layout/grouping-and-alignment.md)와 [spacing-and-adaptivity](https://github.com/jakubkrehel/skills/blob/267330e1adfc66a718fb65fa6918c1f06d0a689e/skills/better-layout/spacing-and-adaptivity.md)를 참고하며 구분선·고정 배수·일률적 행 배치는 채택하지 않는다.

## 로고와 아이콘

요청하거나 제공한 브랜드 자산이 없으면 로고·심벌·워드마크·슬로건을 임의로 만들지 않는다(RUI-08). 기존 아이콘을 골랐어도 제품명 옆에 장식 마크로 붙이면 같은 문제다. 일반 화면 제목만으로 과제를 식별할 수 있으면 충분하다. ‘제품 식별’이라는 사후 설명은 로고 제작 요구의 근거가 아니다.

기능 아이콘은 행동의 의미를 빠르게 이해하는 데 필요할 때 사용한다(RUI-12). React UI는 `lucide-react`를 기본으로 사용한다. HTML/CSS 등 비 React 작업은 공식 Lucide SVG 또는 해당 환경의 공식 패키지를 사용하며 아이콘 때문에 React로 전환하지 않는다. 명시된 기존 디자인 시스템/브랜드 자산 때문에 다른 세트가 필요하면 이유와 범위를 기록하고 혼용을 최소화한다. 편집·추가·전송·뒤로 등 동작을 실제로 표현해야 한다. 임의 SVG 경로, 문자 기호, 의미 없는 장식 아이콘을 급조하지 않는다. 정식 SVG 에셋의 inline 사용은 허용하지만 출처·이름·선/채움·크기를 기록한다. 같은 역할의 기능 아이콘 범위에서 색·선 굵기·시각 크기를 일관되게 적용하고 아이콘 버튼에는 접근 가능한 이름과 충분한 터치 영역을 둔다. 다색 브랜드 자산까지 일괄 통일하지 않는다.

[Lucide React 공식 문서](https://lucide.dev/guide/react)를 기준으로 필요한 아이콘만 명시적으로 import한다. 설치된 버전의 실제 export 이름을 확인하고 크기·색·strokeWidth는 공통 토큰/컴포넌트로 맞춘다. 비 React에서 공식 SVG를 복사할 때도 원본 아이콘 이름·출처·라이선스를 보존한다. 원하는 아이콘이 없다고 비슷한 SVG path를 임의 제작하거나 기존 아이콘을 합쳐 로고를 만들지 않는다. 적절한 기존 대안이나 텍스트 표현을 선택한다.

### 라이브러리 선택과 아이콘 의미는 별도 판단

아이콘의 세부 표시·선 굵기·유효 클릭 영역·상태 교체는 [아이콘 영역 계약](icon-controls.md)을 함께 읽는다. 작은 아이콘과 작은 조작 영역을 혼동하지 않고 이웃 조작·터치·키보드에서 확인한다.

Lucide를 썼거나 CTA 오른쪽에 배치했다는 사실만으로 적절한 아이콘이 되지 않는다. 먼저 클릭 직후 실제 동작을 확인하고 `조작 대상 | 실제 동작 | 아이콘이 암시하는 동작 | 선택 이유 | 아이콘을 빼도 구별되는가`를 대조한다(RUI-12). 주제와 비슷한 모양, 빈 오른쪽 공간, 다른 버튼과의 형식 통일만으로 선택하지 않는다.

예시 선택이 입력창에 내용을 채우고 초점만 옮기는 동작이면 전송·업로드 아이콘을 재사용하지 않는다. 실제 전송 CTA와 다른 행동에 같은 아이콘을 붙여 즉시 실행될 것처럼 보이게 하지 않는다. 기존 윤곽선/표면과 예시 텍스트만으로 조작이 충분히 드러나면 아이콘을 생략한다. 더 명확한 설명이 필요한 경우 실제 동작을 드러내는 짧은 라벨을 검토하되 불필요한 안내를 새로 늘리지 않는다.

다른 Lucide 아이콘으로 교체할 때도 의미가 맞는지 먼저 검토한다. 예를 들어 이동을 하지 않는데 단순히 chevron으로 바꾸거나, 클립보드에 복사하지 않는데 복사 아이콘을 쓰는 것으로 문제를 옮기지 않는다. 실제 동작과 혼동되지 않는 기존 아이콘이 없다면 억지로 붙이지 않는다.

코드의 이벤트/링크와 UI 라벨을 대조하고 나서 실제 화면에서 크기·선·여백·광학 정렬을 확인한다. 출처, 동작 의미, 시각 적합성을 모두 통과해야 한다. 아이콘 없는 윤곽선 버튼은 ‘텍스트 전용 버튼 최소화’ 규칙에 어긋나지 않는다.

## 글자 크기 하한

읽는 UI 텍스트의 기본 하한은 **14 CSS px**다(RUI-09). 본문·입력·주요 행동은 보통16px에서 시작한다. 제한된 공간의 짧은 메타정보·읽기 전용 태그·반복 요약에만 아래 조건을 모두 확인해 **최소12 CSS px** 예외를 적용할 수 있다.

- 간격/배치/중복을 먼저 검토하고,14px에서 생긴 구체적인 공간 문제와 줄일 대상·이유를 기록한다. 화면 전체나 공통body 토큰을 축소하지 않는다.
- 가격·입력값·버튼·탭·필터·날짜/시간 선택·오류·동의·핵심 안내에는 기본 하한을 유지한다. 중요한 이용조건의 목록 요약을 줄이면 상세/확인 단계에 같은 조건을14px이상으로 보존하고 사용자의 판단/동의 전에 노출한다.
- 전용 보조 토큰과 선택자로 범위를 제한하고12px미만 또는 transform 축소로 우회하지 않는다. 원본이12px거나 '모바일이니까'라는 이유만으로 자동 적용하지 않는다.
- 실제 기본/좁은폭에서 글자·아이콘 대비와 읽힘을 보고, 글자 확대 시 잘림·겹침·조건 손실이 없는지 확인한다. 프로젝트 계약에 RUI-09 예외의 적용 대상/근거/값/렌더 증거를 남긴다.

14px는 상한이 아니며 예외가 기본값을 대신하지 않는다. 스크린샷만으로 CSS px를 확정하지 않는다.

## 글자 굵기 하한

읽는 UI 텍스트의 최소 굵기는 **medium(500)**이다. 본문·보조문구·입력값·placeholder·버튼·탭·배지·표·채팅·오류·비활성 상태 모두 500 이상을 사용한다. regular/normal(400), light(300), 가변 폰트의 450 등 500 미만을 사용하지 않는다. 레퍼런스의 얇은 글자는 관찰값으로 기록하되 제품 적용값은 하한을 지킨다.

500은 고정값이나 상한이 아니다. 제목·선택·강조에는 semibold(600), bold(700) 등 역할별 굵기를 유지한다. 보조정보는 굵기를 낮추는 대신 크기 하한·대비를 지키는 색상·간격으로 위계를 만든다. 폰트 굵기는 대비 검증을 대신하지 않는다.

기존 타이포그래피 토큰에 하한을 반영하고 실제 사용처의 computed font-weight, 상속·컴포넌트 덮어쓰기와 `::placeholder`를 확인한다. 폰트 파일/가변 축이 해당 굵기를 지원하는지도 확인한다. `* { font-weight: 500 }`처럼 제목·강조를 평탄화하거나 아이콘 폰트·제공된 로고·이미지 속 글자까지 변경하지 않는다. 정적 레퍼런스의 원래 굵기를 조작하지 않으며, 과거 제품을 자동 수정한 것으로 보고하지 않는다.

## CTA와 선택 컨트롤

먼저 각 조작을 `탐색 / 필터·선택 / 실행 CTA`로 분류한다(RUI-10). ‘전체·할 일·완료’는 필터이고 ‘편집·추가·저장·전송’은 행동이다. 같은 줄에 있어도 같은 모양을 반복해 역할을 섞지 않는다.

- 주요 CTA: 채움 등 명확한 버튼 표면과 실행을 예측할 수 있는 라벨을 둔다.
- 보조 행동: 윤곽선/적절한 표면 또는 의미 있는 아이콘+라벨로 조작임을 구분한다. 편집을 필터와 같은 회색 글자 하나로 두지 않는다.
- 필터·탭: 하나의 선택 그룹으로 묶고 선택 상태가 명확하게 보이도록 한다. 선택된 필터만 거대한 CTA처럼 강조하고 실제 행동은 숨기는 위계를 피한다.
- 텍스트 전용 버튼은 최소화한다. 본문 링크 등 명확한 맥락에 필요한 경우에만 이유를 남긴다. 모든 텍스트에 장식 아이콘을 붙이는 것은 해결이 아니다.

아이콘을 포함하는 CTA는 `실제 동작 | 아이콘 역할 | 순서와 근거`를 정한다. 촬영·앨범처럼 동작을 식별하는 아이콘은 선행 배치를, 다음 단계로 향하는 화살표는 후행 배치를 검토한다. 사용자 명시 순서와 확인된 제품 관례를 우선하며, 추가 아이콘도 역할만으로 왼쪽이나 오른쪽에 고정하지 않는다. 아이콘이 없는 버튼에 장식 아이콘을 억지로 추가하거나 탐색 탭·필터·입력까지 같은 순서로 재배치하지 않는다.

버튼의 표현 계약에는 `아이콘 표시 유무 | 글자와의 실제 시각 간격 | 보이는 아이콘+글자 묶음의 중심 | 아이콘 누락 시 자리 처리`를 포함한다(RUI-12/22). CSS gap뿐 아니라 viewBox 내부 여백과 글자 박스를 확인한다. 로딩 실패로 빈 아이콘 슬롯만 남는 경우에는 의도한 라벨 정렬을 복구하고, 출처가 확인된 inline SVG도 검토한다. 간격값은 제품 토큰과 실제 크기에서 정하며 특정 사례의4px를 공통값으로 고정하지 않는다.

화면 맥락과 관례만으로 행동이 충분히 구별되면 아이콘만 사용하는 버튼도 선택할 수 있다. 접근 가능한 이름·터치 영역·키보드 초점을 유지하고 눌렀을 때 예상 동작과 일치하는지 확인한다. 아이콘만으로 촬영과 업로드 등 서로 다른 행동을 구별하기 어려우면 짧은 라벨을 유지한다.

버튼의 윤곽선은 아래의 장식 구분선 금지와 다르다. hover 없이 기본 상태에서도 역할을 구별하고 focus/pressed/disabled를 확인한다.

## 보조 문구를 놓기 전에 삭제 검토

각 보조 문구에 `누가 지금 어떤 판단을 하는 데 필요한가 / 어느 행동과 연결되는가 / 삭제하면 잃는 정보는 무엇인가`를 묻는다(RUI-11). 답이 없으면 삭제한다. 제목 오른쪽이 비었다고 설명을 채우거나 `space-between`으로 관련 없는 두 문구를 양 끝에 놓지 않는다.

‘날짜와 시간도 함께’는 이번 실패의 예시이지 금칙어가 아니다. 자연어 입력 안내가 필요하면 입력 근처의 짧은 예시 또는 첫 사용 안내 한 곳에 둔다. 제목 옆 힌트·대화 첫 메시지·추천 칩·입력 아래 설명으로 같은 기능을 반복하지 않는다. 저장 범위처럼 사실상 필요한 정보는 숨기지 말고 필요한 시점과 가까운 위치에서 한 번 명확히 전달한다. 슬로건은 작업 정보가 아니다. ‘여러 일은 한 줄에 하나씩’ 같은 선택 기능 설명도 기본 composer에 상시 배치하지 않는다. 입력 가까이 있다는 이유만으로 유지하지 말고 필요하지 않으면 설명 행과 예약 높이를 함께 제거한다.

날짜/수량/상태가 설명·제목·배지에 형식만 바꿔 반복되는지도 검사한다(RUI-24). 예를 들어 월 설명 바로 아래 날짜 제목에 같은 월을 다시 쓰면 필요한 연도까지 고려해 한 곳으로 합친다. 달력 탐색 등 서로 다른 역할이 실제로 있을 때만 별도 표시를 유지한다.

## 구획과 스크롤

영역을 나누는 바는 한 개여도 넣지 않는다(RUI-14). `<hr>`뿐 아니라 border-top/bottom, 빈 요소, pseudo-element, gradient, shadow, SVG 등으로 그린 동등한 선을 포함한다. 탭 하단의 긴 기준선과 활성 탭 밑줄/이동 바도 금지 대상이며 탐색 관례나 레퍼런스에 있다는 이유로 예외 처리하지 않는다. 간격·정렬·묶음·짧은 제목·필요한 표면 차이로 구분한다. 줄을 없앤 자리를 카드·박스·큰 패딩으로 모두 대체하지 않는다. 입력·버튼·포커스·실제 표 데이터의 경계는 컨트롤/정보 역할로 판단하며 장식 구분선과 구별한다.

스크롤은 실제 내용이 가용 공간을 넘을 때만 생겨야 한다(RUI-13). ‘언젠가 길어질 수 있다’는 이유로 짧은 목록에 고정 높이와 overflow를 주지 않는다. 100dvh 프레임 안에 소개·달력·큰 채팅 패널을 쌓아 목록 공간을 줄였다면 먼저 불필요한 영역을 제거하거나 화면을 나눈다. overflow:hidden이나 스크롤바 숨김으로 콘텐츠 접근을 막아서는 안 된다.

빈 목록·1개·소수 항목·긴 목록을 각각 검사한다. 각 스크롤 영역의 clientHeight/scrollHeight, 잘리는 내용, 높이를 소비하는 형제를 실제 뷰포트에서 확인한다. 필요한 긴 대화/모달/문서 스크롤은 허용하되 원본 ORC-F16/G23의 적용·충돌도 남긴다. 키보드·큰 글자·짧은 높이에서 내용이 넘치면 읽고 실행할 수 있는 자연스러운 스크롤을 보존한다.

## 목록과 채팅은 화면 구조부터 결정

‘채팅으로도 만들기’는 목록 아래에 항상 큰 대화 패널을 붙이라는 뜻이 아니다(RUI-15). 목록에서 확인·완료하는 과제와 대화로 생성하는 과제가 서로 공간을 빼앗으면 `할 일 / 대화`처럼 별도 탭·뷰를 우선 검토한다. 짧은 일회성 입력이면 간결한 입력 영역이나 시트도 비교한다. 모든 앱에 탭을 무조건 추가하지 않고 핵심 과제와 전환 비용으로 선택한다.

채팅을 선택했다면 입력창만 닮게 만들지 않는다. 사용자 메시지 → 실제 처리 상태 → 결과·실패 → 수정/재시도의 흐름을 설계한다. 생성된 Todo는 목록과 연결하고 탭을 오가도 초안·선택·대화·목록 상태가 보존돼야 한다. 결과는 반복 메시지 대신 생성 대상과 다음 행동을 명확하게 보여준다. 로컬 동기 처리에 가짜 typing 지연이나 AI 응답을 연출하지 않는다.

최신 메시지 근처에서 전송하면 입력과 결과를 따라갈 수 있어야 한다. 과거 대화를 읽는 중에는 새 응답이 와도 강제로 아래로 끌지 않는다. 키보드 열림·닫힘, 긴 입력, 연속 생성, 실패 후 재전송, 화면 전환과 복귀를 실제로 확인한다. 애니메이션을 추가했다는 이유만으로 ‘스무스한 채팅’이라고 판정하지 않는다.

## Todo 요청에 대한 구조 예시

‘모바일 Todo, 채팅으로도 생성’ 요청에는 목록의 확인·완료를 기본 화면으로 두고 생성 경로를 짧게 제공한다. 지속적인 대화가 필요하면 별도 대화 탭에서 처리하고 생성 결과를 같은 목록 상태에 반영한다. 로고·슬로건·중복 힌트·장식 구분선을 추가하지 않고, 필터와 편집 CTA를 구분한다. 주간 달력도 날짜 탐색이 필요한지 검토한 뒤 선택한다. 이는 구조 판단 예시이며 모든 Todo에 복사할 고정 템플릿이 아니다.

## 화면의 대제목과 의미 태그를 분리해 설계

‘할 일 추가’처럼 현재 화면/시트/대화상자의 목적을 설명하는 제목은 그 표면의 주 제목이다(RUI-20). h2 태그라는 이유로 전역 소제목 스타일을 적용하지 않는다. 접근성 문서 구조에는 적절한 heading level과 aria-labelledby를 쓰고, 시각 역할은 page/surface-title 토큰으로 별도 지정한다.

주 제목은 필드 라벨·설명·버튼보다 명확한 크기/굵기/간격 위계를 가져야 한다. 해당 제품의 기존 주 제목 토큰을 생성 시트에서도 출발점으로 검토하되 실제 레퍼런스·화면 폭·긴 제목으로 확인한다. 모든 제목을 무조건 h1로 바꾸거나 지나치게 키워 공간을 채우지 않는다. 목록·대화·생성·수정의 주 제목을 함께 비교한다.

## 날짜·시간 입력도 제품 컴포넌트로

날짜/시간을 브라우저 기본 input 외형에 맡기지 않는다(RUI-21). 일반 텍스트 입력과 선택형 입력의 높이·패딩·글자·경계·아이콘·포커스·오류·비활성 상태를 공통 토큰으로 맞춘다. 날짜 필드는 선택한 날짜를 읽기 쉬운 한국어 표현으로 표시하고, 미선택 시간에 기본 `--:-- --`를 그대로 보여주지 않는다. 예를 들어 ‘날짜 선택’, ‘시간 선택’처럼 행동과 값 상태를 구별한다.

날짜/시간 선택 UI는 기존의 검증된 접근 가능한 picker를 우선 사용해 제품 스타일을 적용한다. 플랫폼 picker를 사용한다면 제품 스타일의 표시/트리거와 원래 선택 동작을 연결하고, OS 팝업을 앱이 커스텀했다고 주장하지 않는다. 기본 네이티브 UI가 요구와 맞지 않으면 적절한 선택 컴포넌트를 구현·연결한다. 아이콘과 테두리만 바꿨다고 선택 경험 전체를 커스텀했다고 보고하지 않는다.

기능 없이 보이는 가짜 날짜 버튼을 만들지 않는다. 선택/취소/초기화, 기존 값 복원, 오늘 표시, 월 이동, 허용 범위, 키보드/포커스 복귀, 모바일 안전 영역을 실제 검사한다. 표시 문자열과 저장값을 분리하고 날짜가 시간대 변환으로 하루 밀리거나 시간 선택을 생략했는데 임의 시간으로 저장되지 않도록 확인한다. 320px에서 날짜·시간을 무리하게 한 줄로 압축하지 않는다.

## 부모·자식과 상태별 여백의 합 확인

간격 토큰을 썼다는 사실만으로 패딩이 맞는 것은 아니다(RUI-22). 각 영역의 `부모 padding + 자식 margin/gap + 테두리 + 자식 내부 padding`을 나눠 기록하고 최종 시각 거리를 비교한다. 좌우뿐 아니라 위/아래와 첫/마지막 자식도 확인한다.

목록 전체 간격은 부모 gap 또는 행 간격 정책 한 곳에서 관리한다. 완료 상태의 첫 행에만 margin-top을 더해 바깥 여백을 두 번 만들지 않는다. 예컨대 부모 padding8px에 첫 자식 margin-top8px가 더해지면 위쪽은16px, 아래쪽은8px가 될 수 있다. 두 값이 토큰이어도 의도한 대칭이 깨진다. 이는 박스 관계 예시이며 실제 값은 DOM/computed style로 확인한다.

완료/미완료/선택/오류/한 줄/여러 줄/단일 행/마지막 행을 함께 본다. 상태 변화는 배경과 내용 표현을 바꾸더라도 행 위치와 부모 inset을 불필요하게 바꾸지 않는다. 숫자 대칭만 강제하지 말고 의도한 제목-본문 간격 등 역할 차이는 근거와 함께 보존한다. padding 문제를 임의 transform이나 음수 margin으로 가리는 수정은 피한다.

## 목록·대화·폼을 한 제품으로 검증

별도 탭은 별도 디자인 시스템이 아니다(RUI-23). 주 제목, 보조 글자, 배경/표면 단계, 입력·버튼 높이/반경/선, 아이콘, 좌우 기준선, 내용 간격을 화면 간 역할 표로 비교한다. 같은 역할은 같은 토큰과 컴포넌트를 사용하고, 다른 값이면 실제 기능적 차이와 시각 비교 근거를 남긴다.

대화에는 메시지 위계와 전송 흐름이 필요하지만 목록의 톤을 버린 흰 빈 화면과 다른 입력 스타일로 자동 전환하지 않는다. 반대로 목록의 카드를 모든 메시지에 복사할 필요도 없다. 공통 시각 문법 안에서 대화/목록에 필요한 표현 차이만 둔다. 공백을 채우려고 슬로건·중복 예시·장식 카드를 더하지 않는다.

목록 기본/완료, 대화 빈/메시지 있음, 생성/수정 폼을 동일 CSS 폭과 테마로 나란히 놓고 비교한다. 토큰 사용 표뿐 아니라 실제 화면 묶음이 증거다. 어느 한 화면이 충분히 검증되지 않았으면 전 화면의 톤 통일을 완료로 선언하지 않는다.

## 섹션의 의미가 드러나도록 구분

구분선 제거가 섹션 경계 제거를 뜻하지 않는다(RUI-25). 서로 다른 판단/행동을 담당하는 영역은 서비스와 콘텐츠에 맞게 구별한다. 예를 들어 날짜 탐색, 상태 필터, 할 일 목록, 생성 행동의 관계를 정하고 어디가 같은 작업 단위인지 표시한다.

먼저 같은 과제의 요소를 묶고 섹션 내부 간격과 섹션 사이 간격을 구별한다. 정보 위계가 더 필요하면 짧은 섹션 제목, 배경/표면 단계, 정렬 기준선 또는 컨테이너를 선택한다. 표면 단계는 page → section → 필요한 상태 표현의 역할로 정하고, 빈 흰 카드나 무조건적인 중첩 컨테이너를 추가하지 않는다.

관련 필터를 목록에서 지나치게 떼지 않고 생성 행동도 적용 대상을 알 수 있는 위치에 둔다. 모든 섹션에 같은 테두리·그림자·둥근 박스를 반복하지 않는다. 반대로 모든 배경을 같게 하고 간격도 같게 해 서로 다른 작업 덩어리를 구분하지 못하게 만들지 않는다. 단일 과제의 작은 화면은 불필요하게 여러 섹션으로 쪼개지 않는다.

RUI-14의 장식 수평선 금지와 함께 적용한다. 레퍼런스의 그룹 표현이 제품 과제에 적합하면 그 원리를 가져오고, 다른 서비스에는 다른 방식을 선택한다. 실제 화면을 보고 영역의 시작/끝과 소속 관계를 이해할 수 있는지, 제목 없이도 가까운 요소들이 같은 그룹으로 읽히는지 확인한다. 섹션을 구별하려다 패딩·스크롤·중복 제목을 늘린 결과도 다시 검토한다.

## 입력·버튼의 세로 중심과 여러 줄의 읽기 시작점

컨트롤의 정렬은 외곽 박스와 내부 콘텐츠를 나눠 확인한다. 한 줄 입력/placeholder, 버튼 글자와 아이콘은 의도한 컨트롤 높이에서 시각 중심이 맞아야 한다. `align-items:center`가 부모에 있다는 사실만으로 textarea 내부 글자까지 중앙이라고 판단하지 않는다. 자식 높이·line-height·상하 padding·기본 margin·아이콘 viewBox를 실제로 확인한다.

여러 줄 textarea는 글이 위에서부터 읽히고 커서가 자연스럽게 이동해야 한다. 모든 텍스트를 수직/수평 가운데로 강제하지 않는다. 입력이 비었거나 한 줄일 때의 작은 높이와 여러 줄일 때의 증가·상한·스크롤을 함께 설계한다. 실제로 한 줄만 필요한 입력을 크게 만들어놓고 빈 공간에 설명을 넣지 않는다.

composer가 입력 영역과 실행 영역을 나눴다면 각 영역 내부의 의도한 중심/기준선과 두 영역의 간격을 따로 검증한다. 안내 삭제 후 남은 footer/min-height/padding 때문에 placeholder가 위로 붙거나 전송 버튼이 혼자 아래로 처지지 않는지 확인한다. 음수 margin·임의 translate로 한 상태만 맞추지 않는다.

빈 입력·한 줄·여러 줄·긴 placeholder·focus·disabled·글자 확대·좁은 폭에서 텍스트 줄 상자와 버튼/아이콘 박스를 비교한다. 관찰 이미지로 어긋남을 기록하되 정확한 CSS 값과 원인은 DOM/computed style로 확인한다. 부모 박스 정렬과 내부 글자 정렬을 모두 검사한다(RUI-22, ORC-F10/G18).

## 포커스 표시는 조작 대상마다 한 곳에서 담당

일반 입력과 composer 모두 실제 초점은 input/textarea에 두고 시각적 표시는 입력을 감싸는 필드 컨테이너의 inset box-shadow로 담당한다. [토큰 계약](design-tokens.md#경계-상태와-레이아웃을-흔들지-않는-포커스)에 따라 내부 입력의 기본 outline/라이브러리 ring을 해당 컴포넌트 범위에서 제거한다. 입력 자체에 inset shadow를 붙이거나 컨테이너의 border 색만 바꾸는 것도 요구를 충족하지 않는다. 모든 input 또는 모든 요소에 전역 outline:none을 적용하지 않는다.

`:active`는 누르는 동안의 상태이며 지속적인 입력 초점이나 키보드 `:focus-visible`을 대체하지 않는다. 컨테이너의 대체 초점 표시가 실제로 유지되고 식별되어야 한다. `:focus-within`이 있다는 사실만으로 충분하다고 보지 않는다.

같은 컨테이너의 전송 버튼으로 Tab 이동하면 입력과 버튼 중 어디에 초점이 있는지 구별되어야 한다. 입력에만 대응하는 컨테이너 포커스 표시를 해제하고 버튼 자체의 focus-visible을 표시하는 등, 조작 대상에 맞춰 표시 주체를 바꾼다. 컨테이너 링 하나로 내부의 모든 버튼 초점을 똑같이 표시하지 않는다. 오류 경계는 오류 정보이고 포커스는 현재 조작 대상이므로 둘의 역할을 구별하며 오류 표시를 무조건 제거하지 않는다.

포인터로 입력 선택, Tab/Shift+Tab 입력↔전송 이동, 버튼 누름/해제, 오류 상태, 강제 색상/고대비 설정을 확인한다. 시스템 고대비에서 커스텀 색이 사라질 때는 시스템 포커스 표시가 남도록 한다. 각 실제 조작 대상의 포커스 위치가 보이고 같은 입력을 이중으로 강조하지 않는지 검사한다.

### 빈 결과의 정렬

목록에 항목이 없고 안내와 복구 행동만 남으면 둘을 하나의 묶음으로 배치한다. 넓은 빈 영역에서는 중앙 정렬을 검토하고 실제 내용·상위 제목과의 관계로 결정한다. 일반 목록의 좌측 정렬을 기계적으로 이어받거나, 반대로 모든 오류/인라인 안내를 중앙으로 바꾸지 않는다. 확대 시 높이가 자연스럽게 늘고 복구 버튼에 접근할 수 있는지 확인한다.

짧은 목록·빈 상태는 콘텐츠가 가용 높이에 들어가면 스크롤이 없는 것을 기본으로 한다. 문서 높이와 실제 휠/터치 이동량을 확인하고 중첩100vh·중복 하단 패딩·불필요한 overflow:scroll을 원인별로 고친다. 내용이 많거나 확대된 경우의 필요한 스크롤은 보존하고 overflow:hidden으로 가리거나 글자를 줄여 해결하지 않는다. 탄성 overscroll과 실제 내용의 스크롤도 구별한다.
