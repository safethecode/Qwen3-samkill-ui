# 검색 선택과 예시

현재 연결의 도구 설명을 먼저 확인한다. 아래는 확인일 2026-09-06의 대표 라우팅이며 도구 스키마가 바뀌면 현재 스키마를 따른다.

| 요청 | 첫 도구 | 핵심 입력 |
|---|---|---|
| 로그인·온보딩·송금 완료 화면/플로우 | `search_ui_patterns` | `query` |
| 바텀시트·버튼·빈 화면 상태 | `search_components` | `component_type`, 필요하면 `pattern` |
| 화면에 실제 표시된 특정 문구 | `search_by_ocr_text` | `text_query`, 필요하면 `pattern` |
| 특정 앱의 화면 전반 | `filter_by_app` | `app_name` |

앱 + 특정 화면/요소라면 해당 검색 도구의 `app_name` 필터를 쓴다. MAU/인기 순위는 그 정보가 요청됐을 때만 해당 도구로 조회한다.

## 한 검색 의도의 예시

요청: 한국 커머스 모바일 결제 화면의 바텀시트.

```json
{
  "component_type": "바텀시트",
  "pattern": "결제",
  "category": "커머스",
  "country": "한국",
  "platform": "MOBILE",
  "limit": 3,
  "page": 1
}
```

`search_components`의 첫 호출에 함께 전달한다. 필요한 장점/상태가 확보됐다면 같은 근거를 얻으려고 반복하지 않는다. 부족하면 [검색 계획](research-plan.md)에 따라 다음 페이지·같은 의도의 다른 표현·관련 요소/앱을 탐색한다. 단일 의도의 복합 필터 규칙을 제품 전체의 호출 1회 제한으로 해석하지 않는다.

- 웹사이트는 `PC`, 모바일 앱은 `MOBILE`, 모바일 게임은 `GAME`.
- 국가 구분은 `한국`, `아시아`, `글로벌`, `해외`이며 글로벌과 해외를 같은 뜻으로 취급하지 않는다.
- 쇼핑·이커머스는 `커머스`, 헬스는 `운동&건강`. 불명확한 분류를 지어내지 않는다.
- `style_query`는 현재 검색 결과를 필터링하지 않는다. “빨간 버튼만 검색했다”는 주장에 쓰지 않는다.
- “결제 완료 화면”은 문구 검색이 아니다. `search_ui_patterns(query="결제 완료")`처럼 화면 의도로 시작한다.
- “결제 화면의 무료배송 문구”는 `search_by_ocr_text(text_query="무료배송", pattern="결제")`처럼 문구 의도로 검색한다.
- 도구마다 결과 제한 설명이 다를 수 있다. 현재 스키마·접근 제한을 확인하고 이 패키지는 첫 요청에 보수적으로 3개를 요청한다.

실제 앱 사용법이나 화면 업로드·수정 요청은 이 조회 도구의 작업 범위가 아니다.

## 복합 요청의 별도 검색 예시

‘모바일 Todo, 채팅으로도 생성’은 `search_ui_patterns(query="할 일", platform="MOBILE", limit=3, page=1)`과 `search_ui_patterns(query="채팅", platform="MOBILE", limit=3, page=1)`로 서로 다른 과제를 조사한다. 채팅 첫 페이지가 대화방 목록/빈 상태뿐이고 has_more가 있으면 같은 조건 page=2로 실제 입력/메시지 화면 후보를 추가한다. 모바일 화면 전환 근거가 없으면 탭/내비게이션도 적절한 요소 검색으로 보완한다. 이는 호출 계획 예시이며 실제 결과가 적합하면 불필요한 호출은 하지 않는다.

여러 검색의 갤러리는 SC-ID로 구분하고 각 호출 안의 A/B/C 순서를 유지한다. 서로 다른 호출의 A를 같은 출처로 합치지 않는다. 최종 전달은 누적 R-ID와 B-ID별 채택/배제·구현 적용으로 연결한다.
