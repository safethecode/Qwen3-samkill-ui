# 레퍼런스 기반 온보딩 플로우

화면 모음을 사용자의 진입·완료·복구 경로로 연결한다. 레퍼런스에서 본 흐름과 우리 제품에 새로 제안하는 흐름을 구분한다.

대상 레포가 있으면 루트 `DESIGN.md`를 먼저 읽어 제품의 현재 디자인·문구·컴포넌트 기준을 반영한다. 기준 작성/갱신은 `design-md`와 연결하며 읽기 전용 조사·리뷰 범위에서는 파일을 임의 수정하지 않는다.

## 입력과 근거

사용자와 완료 목표, 가입/설정 요구, 선택·필수 정보, 실제 API/제품 정책, 기존 화면과 레퍼런스를 확인한다. 충분한 자료가 있으면 재검색하지 않는다. 필요한 검색은 설치된 `uibowl-research` 또는 현재 도구의 화면/플로우 검색으로 수행한다.

각 R/O-ID에 실제 확인한 화면·순서·동작을 표시한다. 동의 화면 한 장은 가입 전체 흐름의 관찰 증거가 아니다. 여러 정지 화면의 나열로 전이 순서·완료 조건을 확정하지 않는다. 직접 실행/영상으로 확인한 전이만 observed, 사용자 요구는 required, 새 설계는 proposed로 표시한다.

## 설계와 전달

[플로우 계약과 예시](references/flow-contract.md)를 읽고 기존 위치 또는 `design/flow.md`에 작성한다. 작은 흐름은 채팅 표로 충분하다.

1. 시작점, 완료 조건, 최소 필수 정보, 건너뛸 수 있는 단계를 정한다. 사용자 과제와 무관한 환영 슬라이드·프로필 수집·보상 연출을 추가하지 않는다.
2. 화면/상태 S-ID와 전이 T-ID를 만든다. 전이마다 trigger, guard, 처리 중, 성공/실패 목적지, 데이터 보존, 뒤로 가기·재진입 정책을 기록한다.
3. 정상 진입뿐 아니라 기존 계정, 선택 동의 거절, 입력 오류, 네트워크 실패, 응답 미상, 중복 제출, 중단/복귀를 요구 범위에서 다룬다.
4. 필수/선택을 구분한다. 선택 동의 거절이 완료를 막지 않도록 설계한다. 동의 항목·보관 기간·정책 문구를 레퍼런스에서 복제하거나 법적 사실로 만들어내지 않는다.
5. Do/Avoid/Intentional differences/Unknown을 기록한다. 화면 디자인은 설치된 `reference-to-ui`, 문구는 `ux-copy`를 필요한 경우에만 연결한다. 없으면 같은 출처·상태 계약으로 직접 명세한다.

화면 수나 진행률을 꾸미려고 불필요한 단계를 만들지 않는다. 진행률은 실제 필수 단계에 맞춘다. 복구 API가 없으면 결과 조회나 멱등성을 구현된 기능처럼 쓰지 않고 의존성으로 남긴다. 결과 미상 상태를 확정 실패로 취급해 자동 재제출하지 않는다.

## 검증과 종료

구현된 폼·복구 경로는 [내용 경계와 연속 상태 검증](../reference-review/references/state-stress.md)으로 입력 보존·응답 유실·중복 반영·알림과 초점의 수명을 함께 확인한다. 별개 상태의 스크린샷만으로 S/T-ID 사이 전이를 통과시키지 않는다.

시작부터 완료까지, 실패 후 복구, 뒤로/재진입, 선택 거절, 기존 계정 경로의 시나리오를 작성한다. 구현이 있다면 실제로 실행하고 S/T-ID별 결과를 남긴다. 명세 요청은 `spec-only`, 화면/동작을 실행하지 못하면 해당 검증은 `not-verified`다.

산출물에는 관찰된 범위, 제안 흐름, 전이 계약, 확정되지 않은 제품/API 정책, 검증 시나리오가 들어간다. missing 정보가 있어도 독립적으로 정할 수 있는 흐름은 전달한다. 미확인 API를 지어내거나 필요한 질문을 매번 승인 절차로 바꾸지 않는다. 구현·계정 생성·외부 전송은 사용자 요청 범위에서만 수행한다.
