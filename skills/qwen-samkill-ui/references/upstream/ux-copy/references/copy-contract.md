# 문구 전달 계약

## 문자열마다 필요한 항목

| 항목 | 내용 |
|---|---|
| C-ID / key | C1 같은 추적 ID와 실제/예정 문자열 key |
| 화면·상태·노출 조건 | 서버/사용자 행동 중 어떤 조건이 문구를 표시하는지 |
| 필요성과 배치 | 이 문구가 필요한 판단/행동, 삭제 시 잃는 정보, 해당 입력/행동과의 거리. 불필요하면 삭제로 기록 |
| 최종 UI 문구 | 사용자가 볼 내용만. 개발 메모나 출처를 섞지 않음 |
| 연결 행동 | 클릭/다음 단계, 없으면 없음, 미정이면 unknown |
| 사실 근거 | 확인한 제품 사실, 사용자 요구, 참고 R/O-ID; 어조 참고와 동작 근거 분리 |
| 상태 | ready / draft-dependent / blocked-on-fact |
| 검증 | 사실 보존·누른 직후 행동·한국어 8원칙, 긴 변수·좁은 폭·줄바꿈·접근 가능한 이름·상태 일치; 미실행 명시 |

key는 기존 i18n 규칙을 따른다. 코드베이스가 없으면 예정 key라고 표시한다. 길이 제한은 제품 요구 또는 실제 레이아웃으로 정하고 임의의 글자 수를 범용 규칙으로 만들지 않는다.

## 가상 예시: 결제 실패

입력: 화면은 실패로 분류됨. 원인·과금 여부·복구 행동은 미확인. 레퍼런스에는 “결제 실패 / 다시 결제”가 표시된다는 사용자 기록이 있음.

| ID / 예정 key | 노출 조건 | 최종 UI 문구 | 연결 행동 | 근거/상태 | 검증 |
|---|---|---|---|---|---|
| C1 / payment.failure.title | 제품에서 결제 실패로 확정한 상태 | 결제를 완료하지 못했어요 | 없음 | 사용자 제공 실패 상태 / ready | 좁은 폭 줄바꿈, 상태 일치: 미실행 |
| C2 / payment.failure.action | 복구 행동 확정 전 | 미정 — UI에 이 메모를 표시하지 않음 | unknown | 레퍼런스 버튼은 동작 근거가 아님 / blocked-on-fact | 행동 확정 뒤 라벨과 실제 실행 대조 |

필요성과 배치: C1은 처리 상태를 알리는 제목으로 둔다. 같은 실패를 반복하는 설명은 추가하지 않는다. C2는 복구 동작이 확정되면 상태 안내 근처에 둔다.

개발 메모: 과금 여부를 단정하는 설명, 원인 단정, 자동 재결제를 추가하지 않는다. 실제 서버 상태가 실패가 아닌 결과 미상이라면 제목도 “결제 결과를 확인하지 못했어요”처럼 확인된 상태에 맞춰 바꾼다. 화면 이름이 실패라는 이유로 서버 결과까지 실패라고 추정하지 않는다.

## 상태별 적용

- 빈 결과: 실제로 0건인지 조회 실패인지 구분한다. 검색 조건 변경/초기화가 가능할 때 그 행동을 안내한다.
- 처리 중: 실제 진행률이 없으면 숫자나 예상 완료 시간을 만들지 않는다.
- 성공: 완료된 범위를 정확히 말한다. 요청 접수와 처리 완료를 같은 말로 쓰지 않는다.
- 파괴적 행동 확인: 무엇이 바뀌고 대상이 무엇인지, 되돌릴 수 있는지는 확인된 정책으로 쓴다.
- 오류: 알려진 사실과 실행 가능한 복구 행동을 제공한다. 외부 정책이나 법률 판단은 문구 스킬에서 만들어내지 않는다.

## 표현 검토

같은 행동에 다른 라벨을 붙이지 않았는지, 화면 제목과 설명이 같은 말만 반복하는지, 명사형 버튼이 실제 행동을 숨기는지 확인한다. 한국어는 자연스러운 어순과 제품의 어조를 따른다. 친근함을 위해 모든 오류에 감탄사·이모지를 넣지 않는다. 검증 메모는 UI 밖에 둔다.

한국어 문구의 상세 검토는 [한국어 글쓰기 기준](korean-writing.md)을 따른다. 필요한 C-ID에 바꾸기 전/후와 이유를 기록한다. ‘더 자연스러워짐’만 적지 말고 중복 제거, 즉시 행동 예측, 조건 보존처럼 무엇을 개선했는지 쓴다.

## 의미가 겹치는 날짜·수량·상태

문자열 일치만으로 중복을 판단하지 않는다(RUI-24). 상단의 ‘2026년 9월’과 바로 아래 ‘9월 13일 할 일’처럼 같은 월이 다른 형식으로 반복되는지 확인한다. 설명·제목·배지·본문이 같은 날짜/수량/상태를 재진술하면 한 곳으로 합치거나 역할 없는 줄을 삭제한다.

정보 항목별로 필요한 연도/월/일/요일/수량/상태와 실제 소유 위치를 정한다. 연도가 필요하면 ‘2026년 9월 13일 할 일’ 등 한 제목에 보존할 수 있다. 현재 연도가 명확한 작업에서 생략해도 되는지는 과제와 날짜 범위로 판단한다. 글자가 길다는 이유만으로 축소하지 않는다. 기본14px를 유지하고 짧은 보조정보의12px 예외는 [글자 기준](../../reference-to-ui/references/ui-composition.md#글자-크기-하한)에 따라 별도 판단한다. 달력 월 이동 제목과 선택된 날짜의 작업 제목처럼 역할이 다른 경우에는 그 탐색 역할을 확인하고 유지한다. 문구가 다르다는 사실만으로 두 표시가 필요하다고 보지 않는다.

## 선택 기능 안내를 입력창에 상시 붙이지 않기

‘여러 일은 한 줄에 하나씩’ 같은 보조 입력법은 기본 composer의 전송 버튼 옆이나 입력창 아래에 상시 넣지 않는다. 입력과 실행이 이미 명확하면 안내를 삭제한다. 안내를 입력 근처로 옮겼다는 사실만으로 필요한 문구가 되는 것은 아니다(RUI-11).

선택 기능 설명이 실제로 필요하면 사용자가 도움말을 열었거나 해당 입력 방식의 오류를 고치는 시점처럼 구체적인 노출 조건을 정한다. 첫 사용이라는 이유만으로 안내/칩/툴팁을 자동 추가하지 않는다. 필수 형식·비용·오류·유효성 조건을 전달하는 문구는 필요성을 확인해 보존한다. 사용자가 여러 항목을 입력할 수 있다는 기능 자체는 안내 삭제와 무관하게 유지한다.

문구를 제거한 뒤에는 빈 설명 행과 예약 높이도 제거하도록 구현에 전달한다. 어떤 문구인지 외우기보다 현재 사용자의 판단/행동에 실제 도움이 되는지 검사한다.
