# 제품 UX 문구

문구를 사용자 상태와 실행 가능한 다음 행동에 연결한다. 한국어는 사람이 말할 때 쓰는 표현으로 작성한다. 브랜드 어조를 유지하되 상투적인 사과나 추상적인 친절함으로 정보를 대체하지 않는다.

대상 레포가 있으면 루트 `DESIGN.md`를 먼저 읽어 제품의 현재 디자인·문구·컴포넌트 기준을 반영한다. 기준 작성/갱신은 `design-md`와 연결하며 읽기 전용 조사·리뷰 범위에서는 파일을 임의 수정하지 않는다.

## 입력

화면/상태, 사용자 과제, 확정된 제품 동작, 브랜드 어조, 공간 제약, 기존 문자열, 참고 문구를 확인한다. 모르는 원인·처리 결과·과금 여부·시간 약속은 unknown으로 둔다. 선택 정보가 없으면 가정을 표시하고 가능한 문구를 작성한다.

UIbowl 검색이 필요한 요청이면 설치된 `uibowl-research` 또는 현재 도구 설명을 사용한다. 특정 표시 문구는 OCR, 화면/흐름은 패턴 검색이다. 검색은 필요할 때만 한다. 레퍼런스 문구는 표현의 사례이며 우리 서비스의 정책·효과·복구 가능성에 대한 증거가 아니다.

## 작성

문구를 다듬기 전에 필요한 문구인지와 위치를 확인한다. 선택 기능의 입력법을 composer에 상시 붙이지 않는다. 입력과 실행이 명확하면 삭제하고, 실제 도움/오류 시점 등 필요한 노출 조건이 있을 때만 안내한다. 날짜·수량·상태가 제목/설명/배지에서 형식만 달리 반복되는 의미 중복도 검사하고 필요한 정보는 한 곳에 보존한다. 제목 옆 빈 공간을 채우는 힌트·슬로건·중복 설명은 삭제를 우선한다. 필요한 안내는 관련 입력/행동 근처에 한 번 배치하고, 삭제 시 잃는 정보와 노출 시점을 기록한다. 읽는 UI 글자는 기본14 CSS px 이상으로 둔다. 짧은 보조정보의 제한적12px 예외는 [글자 기준](../reference-to-ui/references/ui-composition.md#글자-크기-하한)에 따라 범위와 검증을 남기며, 내용을 숨기기 위한 축소로 쓰지 않는다.

[문구 계약과 예시](references/copy-contract.md)를 읽는다. 각 문자열에 C-ID, 화면/상태와 노출 조건, 최종 문구, 연결 행동, 사실 근거, 검증 방법을 붙인다. UI에 표시할 문구와 구현자를 위한 unknown/주의 메모는 칸을 나눠 쓴다.

한국어 문구는 [한국어 글쓰기 기준](references/korean-writing.md)을 반드시 읽고 8개 원칙으로 검토한다. 다음 행동 예측, 군더더기 단어, 중복 문장, 현재 필요한 핵심 정보, 말하기 쉬움, 선택권, 누구나 이해할 표현, 상황에 맞는 공감을 확인한다. 미래의 혜택을 지금 버튼의 동작처럼 쓰지 않는다.

화면에는 현재 상태와 가능한 다음 행동을 필요한 만큼 전달한다. 버튼은 **누른 직후**의 동작을 드러내는 동사/목적어를 쓴다. 서비스 용어와 호칭·종결어미를 일관되게 유지한다. 금액·주기·날짜·조건·불확실성은 짧게 만들기 위해 삭제하지 않는다. 빈 공간을 채우려고 부제나 설명을 만들지 않는다.

## 피할 선택

- 원인이 불명확한 오류에 “일시적”, “네트워크 문제”, “곧 해결”을 붙이지 않는다.
- 결과가 불명확한 결제에 “청구되지 않았어요”, “다시 결제”를 확정하지 않는다.
- 실패 상황의 “앗!”, 이모지, 반복 사과, “혁신적인 경험” 같은 광고 문구를 기본값으로 쓰지 않는다. 확인된 사실과 행동을 먼저 쓴다.
- 동작이 정해지지 않은 버튼을 그럴듯한 라벨만 붙여 활성화하지 않는다. 문구 초안/연결 대기로 표시하고 확정된 문자열은 전달한다.
- 레퍼런스의 이름·혜택·수치·보장을 우리 제품의 사실로 복제하지 않는다. “전환율이 좋아지는 문구”라고 주장할 실험 근거가 없으면 가설로 쓴다.
- “~에 대한 처리가 수행되었어요” 같은 명사화·피동, 불필요한 소유격·외래어를 그대로 두고 어미만 해요체로 바꾸지 않는다. 바뀐 상태나 사용자의 행동을 쉬운 동사로 쓴다.
- 비용을 숨기거나 “혜택을 포기하시겠어요?”처럼 거절에 죄책감을 주는 표현을 쓰지 않는다. 가능한 선택과 결과를 정확히 보여준다.

## 검증과 종료

AI 문구 탐지 결과를 받았으면 일치를 수정 후보로만 취급한다. 표현을 구체화하려고 수치·원인·복구 기능을 만들지 않는다. 반복 오류나 사라지는 복구 안내는 [상태 검증](../reference-review/references/state-stress.md)에 연결하고 문구 수정 범위와 흐름 수정의 필요를 구별한다. 폰트·줄바꿈·말줄임도 다루는 작업은 [타이포그래피](../reference-to-ui/references/typography.md)를 적용한다.

실제 레이아웃을 사용할 수 있으면 좁은 폭·긴 변수·줄바꿈·스크린리더 이름·관련 상태에서 확인한다. 없으면 문구 명세를 전달하고 레이아웃/행동 검증은 not-verified다. API를 구현하거나 출시 승인까지 범위를 넓히지 않는다.

결과는 기존 문자열 문서 또는 `design/copy.md`에 작성한다. 작은 요청은 채팅 표로 충분하다. 확정 문자열, 조건부 초안, 필요한 제품 사실, 실제 확인한 검증을 구분하면 완료다. 기존 문구를 수정했다면 바꾼 이유와 지킨 사실을 짧게 남긴다. 8원칙 점검은 해당 문구/화면의 근거를 기록하고 매번 전체 체크리스트를 사용자에게 반복하지 않는다. 미확인 복구 동작 때문에 확정 가능한 문구까지 전달하지 않는 일은 피한다.
