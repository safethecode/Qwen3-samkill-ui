# 레퍼런스를 구현 언어로 분해하기

실제 이미지를 확보한 직후, 제품에 맞게 바꾸거나 코드를 만들기 전에 실행한다. 화면을 요소 목록으로만 설명하지 않고 **요소의 계약 + 요소 사이의 관계 + 조립 순서**로 번역한다. 검색은 `uibowl-research`, 제품 적용은 `reference-to-ui`, 결과 판독은 `reference-review`와 연결한다. 이미 유효한 분석이 있으면 재작성하지 않고 바뀐 영역만 보완한다.

## 범위

- 분석: 출처·이미지를 확인하고 아래 계약을 작성한다. 검색 목록만 요청한 작업에 강제하지 않는다. 읽기 전용/명세 전용이면 구현하지 않는다.
- 재현 실험: 사용자가 실제 구현을 포함한 프롬프트 검증이나 요소별 구현을 요청하면 원본, 요소 표본, 프롬프트, 조립 화면을 함께 제공한다. 제품 각색과 분리하고 실제 구현 범위를 명시한다.
- 제품 적용: 분석 후 채택·변경 결정을 Q-ID로 연결한다. 모든 레퍼런스를 별도 앱으로 재현할 필요는 없다.

대상 AGENTS와 DESIGN.md를 읽는다. 사용자 기준과 원본이 충돌하면 원본 관찰을 유지한 채 적용 차이를 따로 기록한다. 한 화면의 사진 크기·색·배치를 공통 프리셋으로 만들지 않는다.

## 번역 계약

[요소·프롬프트 계약](references/element-contract.md)을 사용한다. 원본을 직접 보고 R-ID와 영역을 고정한 뒤 화면 → 의미 있는 묶음 → 개별 요소/변형으로 분해한다. 이미지 접근이 안 되면 `not-inspected`로 남기며 태그나 상식으로 빈칸을 채우지 않는다.

각색·조합 작업은 [화면 스타일 계약](references/element-contract.md#각색-전-화면-스타일-계약)을 먼저 공유 입력에 넣는다. 원본 색 이름 대신 색·표면·그림·간격이 만드는 관계를 관찰하고, 커스텀 값은 그 관계와 연결한다.

E-ID마다 역할, 부모/형제, 박스와 사방 여유, 정렬, 실제 내용과 줄바꿈, 글자/색/아이콘/경계, 관찰된 상태, 미확인, 조립 관계를 작성한다. 공통 속성은 공유 계약에 한 번 두고 변형에는 차이만 적는다. 상세 측정은 [컴포넌트 분석](../uibowl-research/references/component-anatomy.md)을 따른다.

원본 관찰(O), 구현 선택(D), 검증(Q/V)을 섞지 않는다. image-px와 CSS-px를 구별하고 배율은 비교 조건으로 기록한다. 원본 CSS/DPR를 모른다고 관계까지 unknown으로 만들거나 추정값을 실측으로 바꾸지 않는다.

효과의 구현 방법까지 분석할 때는 `실측 값 | 그 값에서 계산한 관계 | 의도/기술 가설`을 구별한다. 라이브 페이지에서는 배경→이미지/효과→오버레이→내용과 pseudo-element의 겹침 순서, 적용된 스타일, 클리핑·opacity를 확인하고 각 층이 무슨 효과를 만드는지 설명한다. 정지 이미지만 있다면 가능한 재현 방식이며 실제 CSS·라이브러리의 복원이라고 하지 않는다. 픽셀 샘플도 해당 이미지 위치의 색일 뿐 원본 토큰이나 전체 대비 인증이 아니다. 원본 분석 요청을 이유로 효과를 실제 제품에 추가하지 않는다. 이 보완은 [Jakub explain-interface](https://github.com/jakubkrehel/skills/tree/267330e1adfc66a718fb65fa6918c1f06d0a689e/skills/explain-interface)의 근거 구별과 층별 설명을 참고한다.

## 프롬프트로 재현해 확인하기

실험에서는 **공유 계약 + 선택한 E-ID의 프롬프트 + 명시된 에셋 + 조립 계약**을 구현 입력 묶음으로 고정한다. 요소 설명만 떼어 주면서 누락된 공유 값을 알아서 채우게 하지 않는다. 프롬프트 버전·입력 파일·출력 파일·원본을 봤는지를 기록한다. 독립 구현 평가를 사용하면 원본은 분석 담당만 보고 구현 담당은 고정 입력만 받는다. 같은 에이전트가 원본을 봤다면 비공개 재현 평가로 부르지 않는다.

독립 요소와 조립 화면은 같은 컴포넌트·토큰을 사용한다. 사용자에게 원본 영역 → E-ID → 실제 입력 프롬프트 → 구현 표본 → 조립 결과를 대응시켜 보여준다. 사진 에셋만 분리해 사용하는 것과 UI 전체를 이미지로 덮는 것을 구별한다. 정지 이미지에 없는 동작은 미확인으로 유지하고, 동작 구현이 요청된 경우에만 별도 결정으로 설계한다.

같은 표시 폭에서 먼저 구조·비율·밀도, 다음 세부 표현을 대조한다. 프롬프트를 수정하기 전 최초 입력과 렌더를 보존한다. 구현이 계약을 어겼는지, 계약이 원본을 잘못 읽었는지, 입력이 모호했는지를 나눠 최소 수정한다. 수정 후 실제 렌더로 다시 확인한다.

## 사용자 교정을 쌓기

[재발 점검](../reference-review/references/feedback-regression.md)으로 교정을 의미/관계/스타일/동작/검증 누락으로 구별하고 공유 계약의 적용처를 찾는다. 특정 px·색만 추가하는 대신 왜 이전 번역이 실패했는지, 어느 화면/상태에 다시 적용할지를 입력에 반영한다.

사용자가 지적하면 [교정 기록 형식](references/element-contract.md#교정-기록)에 원문 요지, E-ID/관계, 기대/실제, 원인 가설, 수정 프롬프트, 재렌더 결과를 순서대로 추가한다. 원인 확인 전 스킬의 새 보편 규칙으로 확정하지 않는다. 재사용할 해석 원리는 적용 조건과 반례를 함께 스킬에 보완하고, 해당 화면의 좌표·색은 사례에 남긴다.

이전 실패·프롬프트·증거는 보존한다. 사용자의 미응답은 품질 승인이 아니다. 이번 실험의 판독과 실제 제품의 전체 시각·행동 게이트를 구별하고 검증하지 않은 정확도나 범용성을 주장하지 않는다.
